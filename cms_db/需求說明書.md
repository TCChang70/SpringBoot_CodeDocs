## 1. 專案概述

本系統為一套通用型內容管理系統（CMS），提供使用者帳號管理、文章撰寫與發佈、分類與標籤組織、留言互動及多媒體檔案管理等核心功能。系統採用資料庫 `cms_db` 作為唯一資料來源。

### 1.1 系統目標

- 提供文章內容的建立、編輯、審核、發佈與封存之完整生命週期管理。
- 支援多角色權限控管（管理者、編輯、作者、訂閱者）。
- 提供彈性的內容分類（多層階層式分類）與標籤標記機制。
- 支援文章留言與互動管理（審核、垃圾留言過濾）。
- 提供多媒體檔案的上傳、引用與管理。

## 3. 使用者角色定義

| 角色代碼 | 角色名稱 | 權限說明 |
|---|---|---|
| `admin` | 管理者 | 系統最高權限，可操作所有模組、管理所有使用者與角色指派、審核文章 |
| `editor` | 編輯 | 可撰寫與編輯文章、審核其他作者之待審文章、管理分類與標籤 |
| `author` | 作者 | 可建立與編輯自己的文章（草稿／待審），無法直接發佈 |
| `subscriber` | 訂閱者 | 可登入、瀏覽文章、發表留言，無法新增或編輯內容 |

## 4. 功能性需求（Functional Requirements）

### FR-01 使用者帳號管理（users）

| 編號 | 需求描述 |
|---|---|
| FR-01-01 | 系統須提供使用者註冊功能，欄位包含帳號（`username`）、電子郵件（`email`）、密碼（`password`）。 |
| FR-01-02 | `username` 與 `email` 須為全域唯一（Unique Index）。 |
| FR-01-03 | 密碼不得以明文儲存，須以雜湊值存放於 `password_hash` 欄位。 |
| FR-01-04 | 每位使用者須指派一個角色（`role`），預設角色為 `author`。 |
| FR-01-05 | 管理者可查詢、修改、停用或刪除使用者帳號，並可變更其角色。 |
| FR-01-06 | 使用者可維護個人資料：顯示名稱（`display_name`）、頭像（`avatar_url`）。 |
| FR-01-07 | 建立時自動記錄 `created_at`，資料異動時自動更新 `updated_at`。 |

### FR-02 文章管理（articles）

文章狀態流程如下：

```
draft（草稿） → pending_review（待審核） ⇄ published（已發佈） ⇄ archived（已封存）
```

| 編號 | 需求描述 |
|---|---|
| FR-02-01 | 作者可建立文章，欄位含標題（`title`）、網址代稱（`slug`）、摘要（`summary`）、內文（`content`）、精選圖片（`featured_image`）。 |
| FR-02-02 | `slug` 須為全域唯一，作為文章永久網址。 |
| FR-02-03 | 新建文章預設狀態為 `draft`，僅作者與具權限之角色可見。 |
| FR-02-04 | 作者可將文章送交審核，狀態轉為 `pending_review`。 |
| FR-02-05 | 編輯或管理者可審核文章：核准後轉為 `published`，退回則維持 `pending_review` 或 `draft`。 |
| FR-02-06 | 每篇文章須指定作者（`author_id`，關聯 `users`）。 |
| FR-02-07 | 文章可設定發佈時間（`published_at`）；發佈時系統須自動記錄該時間。 |
| FR-02-08 | 系統須記錄文章被瀏覽次數（`view_count`），預設為 0。 |
| FR-02-09 | 已發佈文章可封存（`archived`），封存後對一般使用者隱藏，但仍保留於系統。 |
| FR-02-10 | 文章可指派多個分類與多個標籤（多對多關聯）。 |

### FR-03 分類管理（categories）

| 編號 | 需求描述 |
|---|---|
| FR-03-01 | 分類欄位含名稱（`name`）與網址代稱（`slug`），`slug` 須為唯一。 |
| FR-03-02 | 分類支援多層階層結構，透過 `parent_id` 自我關聯，`parent_id` 為 NULL 代表頂層分類。 |
| FR-03-03 | 系統須防止分類自我參照（不得將自身設為父分類）或形成循環階層。 |
| FR-03-04 | 分類可填寫描述（`description`）說明用途。 |
| FR-03-05 | 刪除分類時，系統須決定其下文章與子分類的處理方式（禁止刪除、轉移或連帶處理）。 |

### FR-04 標籤管理（tags）

| 編號 | 需求描述 |
|---|---|
| FR-04-01 | 標籤欄位含名稱（`name`）與網址代稱（`slug`），兩者皆須唯一。 |
| FR-04-02 | 標籤為扁平結構（無階層）。 |
| FR-04-03 | 一篇文章可掛多個標籤；一個標籤可被多篇文章使用（多對多）。 |

### FR-05 留言管理（comments）

| 編號 | 需求描述 |
|---|---|
| FR-05-01 | 登入使用者可直接以帳號留言（記錄 `user_id`），未登入訪客填寫 `author_name`、`author_email` 留言。 |
| FR-05-02 | 留言須歸屬於特定文章（`article_id`）。 |
| FR-05-03 | 留言支援巢狀回覆，透過 `parent_id` 自我關聯；頂層留言 `parent_id` 為 NULL。 |
| FR-05-04 | 新留言預設狀態為 `pending`（待審核）。 |
| FR-05-05 | 管理者／編輯可核可留言（`approved`）或標記為垃圾（`spam`）。 |
| FR-05-06 | 一般使用者僅可瀏覽 `approved` 狀態之留言。 |

### FR-06 多媒體管理（media）

| 編號 | 需求描述 |
|---|---|
| FR-06-01 | 系統須支援檔案上傳，欄位包含檔名（`file_name`）、儲存路徑（`file_path`）、檔案類型（`file_type`）、檔案大小（`file_size`）。 |
| FR-06-02 | 上傳時須記錄上傳者（`uploader_id`，關聯 `users`）。 |
| FR-06-03 | 檔案可設定替代文字（`alt_text`），供無障礙與搜尋引擎使用。 |
| FR-06-04 | 系統須限制上傳檔案類型與大小（由業務規則另行定義）。 |
| FR-06-05 | 上傳檔案可被文章（精選圖片）或內文引用。 |

### 5.3 資料完整性規則

- **唯一性**：`users.username`、`users.email`、`articles.slug`、`categories.slug`、`tags.name`、`tags.slug` 具唯一索引。
- **參照完整性**：全部外部鍵（FK）於資料庫層級強制實施，禁止建立孤兒紀錄。
- **多對多中介表**：`article_categories`、`article_tags` 使用複合主鍵，一篇文章對同一分類／標籤僅能關聯一次。
- **串聯刪除策略**：多對多中介表於文章刪除時採取連帶刪除（CASCADE）；分類／標籤刪除時連帶移除對應關聯。

## 6. 非功能性需求（Non-Functional Requirements）

### NFR-01 效能

- 熱門查詢（文章列表、分類與標籤篩選）須建立索引，支援一般流量下頁面回應時間 ≤ 2 秒。
- `articles.status`、`articles.title`、`articles.author_id` 建議建立索引以加速篩選。

### NFR-02 安全性

- 密碼一律以 BCrypt（或同等安全演算法）雜湊，禁止明文儲存或記錄於 Log。
- 對未授權存取（含直接存取其他使用者草稿）須進行權限認證與授權檢查。
- 留言、表單輸入須進行注入（SQL／XSS）防護。
- 檔案上傳須驗證 MIME 類型與大小，防範上傳惡意可執行檔。

### NFR-03 資料備援與復原

- 每日自動備份 `cms_db`，保留至少 7 日備份。
- 提供災難復原（DR）程序，目標復原時間（RTO）≤ 4 小時、復原點（RPO）≤ 1 日。

### NFR-04 擴充性

- 資料量成長時，文章內文（`longtext`）與靜態資源分離儲存。
- 多媒體檔案採用可擴充之儲存（本機磁碟或物件儲存服務）。

### NFR-05 可用性

- 系統目標可用性 ≥ 99.5%。
- 使用者操作介面採繁體中文，並符合一般無障礙規範。

## 7. 驗收準則（Acceptance Criteria）

| 編號 | 驗收項目 |
|---|---|
| AC-01 | 全資料表可經由資料庫 Migration 或 SQL 腳本於乾淨環境重建成功。 |
| AC-02 | 以 `admin` 角色登入後可完成使用者新增／角色變更／停用操作。 |
| AC-03 | 作者完成之文章依流程 draft → pending_review → published 全流程驗證通過。 |
| AC-04 | 未登入訪客留言預設為 `pending`，審核通過後始顯示於文章。 |
| AC-05 | 文章可成功指派多個分類與標籤，關聯紀錄正確寫入中介表。 |
| AC-06 | 以發布環境執行整批 CRUD 測試，交易完整性（含 FK 約束）無違例。 |
| AC-07 | 所有唯一欄位重複輸入時，系統回傳明確錯誤訊息且不產生重複資料。 |
