## 1. 分析目的

本文件依《需求書》進行系統分析，將需求轉化為：
- 使用案例（Use Case）模型與詳細流程
- 資料流程架構
- 角色權限分配
- 系統層次與模組相依結構

供後續《系統設計書（SD）》與程式開發之依據。

## 2. 系統定位

- 系統類型：餐廳內部門市 POS（銷售點）管理系統
- 使用場景：店內點餐、結帳、每日對帳
- 儲存：單一 MySQL 資料庫 `restaurant_pos`

## 3. 角色與權限分析

### 3.1 角色定義

| 角色 | 代表對象 | 說明 |
| --- | --- | --- |
| ADMIN | 店長／管理者 | 可執行所有功能，含帳號管理與每日結帳 |
| STAFF | 一般員工／服務生 | 負責桌位開單、點餐與結帳作業 |

### 3.2 角色-功能權限矩陣

| 功能 | ADMIN | STAFF |
| --- | --- | --- |
| 登入系統 | V | V |
| 員工帳號維護（新增/停用） | V | - |
| 桌位維護 | V | - |
| 菜單維護 | V | - |
| 桌位開單 | V | V |
| 點餐／加點／取消訂單 | V | V |
| 結帳收款 | V | V |
| 每日結帳 | V | - |
| 交易紀錄查詢 | V | - |

### 3.3 登入與啟用規則

- 以 `username` + `password`（雜湊比對）登入。
- `active=0` 之員工不得登入系統。
- 登入成功後系統回傳員工角色，前端依角色顯示可用功能。

### 4.3 使用案例詳細說明

#### UC-01 登入系統
- **主要流程**
  1. 員工輸入帳號與密碼。
  2. 系統驗證帳號存在、`active=1` 且密碼雜湊相符。
  3. 系統建立登入狀態並回傳角色。
- **例外流程**
  - E1 帳號不存在或密碼錯誤 → 顯示「帳號或密碼錯誤」。
  - E2 帳號已停用（active=0）→ 顯示「帳號已停用，請聯絡管理者」。

#### UC-02 維護員工帳號
- **主要流程**
  1. ADMIN 輸入帳號、密碼、姓名、角色。
  2. 系統檢查帳號唯一性並以雜湊儲存密碼。
  3. 系統儲存並記錄 `created_at`。
- **替代流程**
  - ADMIN 可停用/啟用既有員工帳號（active 切換）。
- **例外流程**
  - 帳號重複 → 顯示「帳號已存在」。

#### UC-03 維護桌位
- **主要流程**
  1. ADMIN 新增桌號與容納人數。
  2. 系統檢查桌號唯一性並儲存，狀態預設 `AVAILABLE`。
- **例外流程**
  - 桌號重複 → 顯示「桌號已存在」。

#### UC-04 維護菜單
- **主要流程**
  1. ADMIN 新增/修改菜單名稱、分類、單價、描述。
  2. 系統儲存並維護 `available`（上架/停售）與更新時間。
- **業務注意**
  - 停售項目仍保留於 `menu_item`，僅不可再下單。

#### UC-05 開立訂單
- **主要流程**
  1. STAFF 選擇桌位。
  2. 系統建立 `orders`，狀態 `OPEN`、`total_amount=0`，記錄員工。
- **例外流程**
  - 桌位不可用 → 提示該桌位目前不可開單。

#### UC-06 點餐／加點
- **主要流程**
  1. STAFF 選擇可販售菜單項目（`available=1`）。
  2. 輸入數量；若為飲料可選糖度、冰塊，可加備註。
  3. 系統計算 `subtotal = unit_price × quantity` 並累加訂單 `total_amount`。

- **例外流程**
  - 訂單已 `PAID`／`CANCELLED` → 不可加點。

#### UC-07 取消訂單
- **主要流程**
  1. STAFF 對 OPEN 訂單執行取消。
  2. 系統將狀態改為 `CANCELLED`。
- **例外流程**
  - 訂單已付款 → 不得取消，須以退款流程處理（本次需求範圍外）。

#### UC-08 結帳收款
- **主要流程**
  1. STAFF 選擇付款方式（現金/信用卡/Line Pay）並輸入收款金額。
  2. 系統建立 `payment`（一單一付款唯一限制）、更新 `orders.status=PAID` 並記錄 `paid_at`。
- **例外流程**
  - 訂單已付款 → 拒絕重複收款。
  - 訂單無明細 → 拒絕結帳。

#### UC-09 每日結帳
- **主要流程**
  1. ADMIN 對指定交易日執行結帳。
  2. 系統統計該日 `PAID` 訂單數與營收、依付款方式拆算現金/信用卡/其他金額。
  3. 系統寫入 `daily_closing`（`closing_date` 唯一），記錄執行者與時間。
- **例外流程**
  - 該日已結帳 → 拒絕重複結帳（唯一鍵限制）。
  - 當日尚無已付款訂單 → 仍可結帳（金額為 0）或提示確認。

#### UC-10 查詢交易紀錄
- **主要流程**
  1. ADMIN 依日期/桌位/員工/狀態查詢訂單、明細與付款紀錄。
  2. 系統回傳交易與結帳彙總資料，供對帳。

## 5. 資料流程分析

### 5.1 Level-0 Context Diagram

```
                +------------------------------+
  訂單資料      |                              |
-------------->|      Restaurant POS 系統       |-----> 資料庫 restaurant_pos
  付款資料      |     (P 處理程序群組)          |<----- 讀取桌位/菜單/員工
-------------->|                              |
  結帳指令      |                              |
-------------->|                              |
                +------------------------------+
```

### 5.2 Level-1 資料流程（主要處理程序）

```
  STAFF       P1.登入驗證                      員工作業：P2 開立訂單、P3 點餐/加點、
   │                │                               P4 取消訂單、P5 結帳收款
   │ 帳號密碼       ▼
   └──────────> [ 驗證 ] ──> 員工資料(讀)
                 │成功
                 ▼
      P2 開單 ── order_id ──┐
      P3 加點 ── 明細資料 ──┤
      P4 取消 ── 狀態更新 ──┼──> D orders / D order_item / D menu_item / D restaurant_table
      P5 結帳 ── 付款寫入 ──┤
                            ▼
      ADMIN      P6 每日結帳 ──統計──> D daily_closing / D payment
```

## 8. 系統層次與模組分析

### 8.1 邏輯分層

| 層次 | 職責 | 對應範圍 |
| --- | --- | --- |
| 表現層（UI） | 登入、點餐、結帳、結帳報表畫面 | 全部模組 |
| 應用服務層（Application） | 使用案例流程控制、交易邊界 | UC-01~10 |
| 領域層（Domain） | 訂單、付款、結帳等業務規則計算 | BR-01~07 |
| 資料存取層（Data / Repository） | 持久化至 restaurant_pos | 7 張資料表 |

### 8.2 模組相依

```
M1 員工管理 ←── 登入（所有模組依賴）
M4 點餐管理 ──> M2 桌位管理（讀取桌位）
M4 點餐管理 ──> M3 菜單管理（讀取菜單）
M5 結帳付款 ──> M4 點餐管理（依存訂單）
M6 每日結帳 ──> M5 結帳付款（統計付款）
M6 每日結帳 ──> M1 員工管理（記錄執行者）
```

## 9. 非功能需求分析（映射）

| 需求書編號 | 分析對策 |
| --- | --- |
| NFR-01 | 資料庫層統一 utf8mb4 / utf8mb4_unicode_ci |
| NFR-02 | 金額一律 DECIMAL，禁止 Float/Double |
| NFR-03 | 以資料庫 Foreign Key 約束保證參照完整性 |
| NFR-04 | 密碼以 BCrypt 等單向雜湊儲存，Length 255 |
| NFR-05 | 應用/資料庫時區固定 Asia/Taipei (UTC+8) |
| NFR-06 | 交易表不提供實體刪除，僅狀態變更 |
| NFR-07 | 提供交易查詢與每日結帳報表 |
