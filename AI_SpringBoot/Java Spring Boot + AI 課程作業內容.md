這套課程作業評分標準（Rubric）專為「Java Spring Boot \+ Data JPA \+ SPA 前端 \+ AI 輔助」**設計。評分核心在於**「AI 參與度與思維能力」：要求學員必須展示 Prompt 設計邏輯、Code Review 記錄以及對 AI 生成程式碼的理解與重構過程。

## **一、 課堂作業整體評分權重 (Overall Grading Weights)**

| 評分面向 | 權重 | 說明與標準 |
| :---- | :---- | :---- |
| **技術實作與功能性** | 40% | 程式碼能否正確執行、架構是否符合 Spring Boot / JPA 規範、前後端 API 對接是否成功。 |
| **AI 應用與提示詞工程** | 30% | 是否附上完整 **AI 互動紀錄 (Prompt Log)**、Prompt 是否具備明確 Context 與 Constraint。 |
| **程式碼理解與重構 (Code Review)** | 20% | 能否修正 AI 的潛在 Bug（如 N+1、安全漏洞）、註解是否能清晰說明邏輯。 |
| **程式碼風格與規範** | 10% | 包結構（Controller/Service/Repository/DTO）、命名規範、Git Commit 規範。 |

## **二、 每週課堂作業內容與詳細 Rubric**

### **第 1 週：AI 夥伴環境搭建與第一個 REST API**

* **作業題目**：建立「個人圖書/影音收藏管理系統」的 Spring Boot 專案，設計包含 CRUD 的初始 API。  
* **交付物**：Git 儲存庫連結 \+ AI Prompt 紀錄檔 (prompts\_week1.md)。

#### **第 1 週評分標準 (Rubric)**

| 評分項目 | 優秀 (90-100分) | 良好 (75-89分) | 需改進 (60-74分) | 不合格 (\<60分) |
| :---- | :---- | :---- | :---- | :---- |
| **RESTful API 實作 (40%)** | 完整實現 GET/POST/PUT/DELETE，正確使用 HTTP 狀態碼與 REST 命名規範。 | 完成主要 CRUD 功能，但 HTTP 狀態碼或路由命名有小瑕疵。 | 僅實現部分 API（如只有 GET/POST），且路由設計混亂。 | 程式碼無法編譯或 API 無法正常發送請求。 |
| **AI Prompt 設計 (30%)** | 包含角色設定、Context (Spring Boot 3 / Java 17+) 與明確輸出格式要求。 | 有提供基本 Prompt，但缺乏 Constraint（如未指定 Java 版本或註解要求）。 | 僅輸入簡單指令（如「幫我寫一個 Controller」），完全依賴預設輸出。 | 未提交 Prompt 紀錄檔，或直接複製貼上無互動紀錄。 |
| **理解與註解 (20%)** | 每段 AI 生成的 Controller 方法皆附上清晰的 JavaDoc 說明與思維流程。 | 大部分程式碼有註解，但對關鍵註解（如 @RestController）理解模糊。 | 僅有少量預設註解，無法說明 API 執行邏輯。 | 無任何註解，無法說明 AI 生成內容。 |
| **規範與架構 (10%)** | 嚴格遵守 Controller-Service 分層，pom.xml 無冗餘依賴。 | 結構完整，但邏輯偶爾滲透至 Controller 層。 | 檔案結構混亂，所有邏輯寫在單一類別中。 | 專案結構不完整，無法建置。 |

### **第 2 週：資料庫設計、Data JPA 與 Entity 映射**

* **作業題目**：根據「圖書/影音系統」的業務需求（需包含「作者與書籍 1:N 關聯」），設計 MySQL DDL 並轉為 Spring Data JPA Entity。  
* **交付物**：DDL 腳本、Entity 類別、AI 生成 100 筆測試資料的 SQL 檔、ER 圖。

#### **第 2 週評分標準 (Rubric)**

| 評分項目 | 優秀 (90-100分) | 良好 (75-89分) | 需改進 (60-74分) | 不合格 (\<60分) |
| :---- | :---- | :---- | :---- | :---- |
| **JPA 關聯與 Entity (40%)** | 正確設置 @ManyToOne / @OneToMany、主鍵生成策略與 Cascade/Fetch 類型。 | 關聯設置基本正確，但外鍵名稱或雙向關聯設置有微小瑕疵。 | 僅使用單表，未建立實體關聯，或 @Id 設置錯誤。 | Entity 無法正常映射至 MySQL 資料庫。 |
| **AI 資料生成與測試 (30%)** | 利用 AI 生成具備真實感且符合約束 (Constraint) 的 100 筆測試資料。 | 順利生成資料，但部分欄位邊界條件不符（如字串過長或日期異常）。 | 資料筆數不足或大量重複，未利用 AI 限制邊界。 | 未生成測試資料，無法驗證 JPA 連線。 |
| **Prompt Engineering (20%)** | 輸入明確 DDL 並要求 AI 轉換為 Lombok \+ JPA 格式，附帶轉換邏輯對照表。 | 使用 Prompt 生成 Entity，但手動修正了大量 AI 語法錯誤。 | 提示詞缺乏型別映射說明（如將 MySQL DATETIME 誤轉為 java.util.Date）。 | 無 Prompt 記錄，直接複製貼上網頁生成代碼。 |
| **資料庫規範 (10%)** | 欄位命名符合 snake\_case 與 camelCase 映射，包含必要索引設計。 | 命名基本規範，但未定義主鍵或外鍵約束。 | 命名混亂（中英文夾雜或大寫混用）。 | 資料庫結構無法建立。 |

### **第 3 週：Service 層業務邏輯與 JPA 高級查詢 (含 N+1 檢測)**

* **作業題目**：實現多條件動態篩選與分頁 API，並使用 AI 檢測與修復 N+1 查詢問題。  
* **交付物**：Service/Repository 程式碼、SQL 日誌對比報告 (Optimization Log)。

#### **第 3 週評分標準 (Rubric)**

| 評分項目 | 優秀 (90-100分) | 良好 (75-89分) | 需改進 (60-74分) | 不合格 (\<60分) |
| :---- | :---- | :---- | :---- | :---- |
| **JPA 分頁與查詢 (40%)** | 成功實現 Pageable 分頁查詢與 Derived Query / @Query 自訂查詢。 | 分頁功能正常，但條件篩選邏輯不夠靈活（缺少動態判斷）。 | 查詢語法錯誤，或未實現分頁（直接回傳 List）。 | Service 層邏輯無法順利執行。 |
| **N+1 問題診斷與重構 (30%)** | 主動捕捉 Hibernate N+1 日誌，並引導 AI 使用 JOIN FETCH / @EntityGraph 解決。 | 在提示下發現 N+1 問題並完成修復，但未能詳細說明修復原理。 | 發現 SQL 查詢過多，但未正確重構 Repository（依然產生 N+1）。 | 未進行 SQL 日誌分析，無視效能問題。 |
| **DTO 轉換與封裝 (20%)** | 嚴格隔離 Entity 與 DTO，使用 AI 輔助產生自動轉換邏輯（如 MapStruct）。 | 使用 DTO 傳輸，但手動進行大量 Setter/Getter 轉換且有重複代碼。 | 直接將 Entity 回傳給前端，曝露敏感欄位。 | 未使用 DTO，混淆資料傳輸與持久層物件。 |
| **邏輯與交易管理 (10%)** | 正確使用 @Transactional，例外發生時能正確 Rollback。 | 有使用 @Transactional，但加在不適當的位置（如 Controller）。 | 未考量資料一致性，缺少交易控制。 | 程式碼執行出現資料不一致。 |

### **第 4 週：健壯性 API、例外處理與 OpenAPI 文件**

* **作業題目**：導入 @ControllerAdvice 全域例外處理、前端參數 Validation 驗證與 Swagger API 文件。  
* **交付物**：API 規格文件 URL (Swagger UI)、全域例外處理器、Postman Collection。

#### **第 4 週評分標準 (Rubric)**

| 評分項目 | 優秀 (90-100分) | 良好 (75-89分) | 需改進 (60-74分) | 不合格 (\<60分) |
| :---- | :---- | :---- | :---- | :---- |
| **全域例外與 Validation (40%)** | 統一 API 回傳格式，正確攔截 MethodArgumentNotValidException 與自訂 BusinessException。 | 有全域例外處理，但回傳格式不一致或漏掉部分驗證例外。 | 僅用 try-catch 包裹單一 Controller，未做到全域攔截。 | 系統出錯時直接爆出 500 Stack Trace。 |
| **AI 輔助錯誤分析 (30%)** | 展示將 Stack Trace 貼給 AI 並獲取正確修復方案的對話紀錄。 | 能利用 AI 解釋錯誤訊息，但修復過程過於被動（盲目貼上試錯）。 | AI 提示詞模糊（如「為什麼錯了」），導致 AI 給出不相關解答。 | 未使用 AI 分析錯誤，手動摸索且未修復。 |
| **OpenAPI / Swagger (20%)** | 利用 AI 補全註解，SwaggerUI 能清楚展示欄位說明、範例與 回應碼。 | 成功整合 Swagger，但欄位缺乏中文說明或範例數據。 | Swagger 無法啟動，或僅有預設路由無詳細註解。 | 完全未整合 API 文件工具。 |
| **程式碼乾淨度 (10%)** | 無冗餘試驗代碼，例外訊息語系統一且具備業務意義。 | 程式碼乾淨，但部分例外訊息過於籠統（如「系統錯誤」）。 | 殘留大量 System.out.println 除錯訊息。 | 程式碼排版混亂。 |

### **第 5 週：前端 SPA 框架整合與 API 異步對接**

* **作業題目**：使用前端框架（Vue/React/Angular）建立前端專案，對接後端 RESTful API，實現圖書列表、新增與刪除功能。  
* **交付物**：前後端整合專案、CORS 設定檔、前端 API 模組。

#### **第 5 週評分標準 (Rubric)**

| 評分項目 | 優秀 (90-100分) | 良好 (75-89分) | 需改進 (60-74分) | 不合格 (\<60分) |
| :---- | :---- | :---- | :---- | :---- |
| **前後端連通與 CORS (40%)** | 後端正確配置 CORS，前端順利調用 API 並處理異步狀態（Loading, Error, Success）。 | 能夠成功請求資料，但缺少載入中 (Loading) 或錯誤提示機制。 | CORS 設置採用完全放開 (\*) 且前端異步處理常有 Unhandled Rejection。 | 前後端無法對接，存在跨域封鎖或語法錯誤。 |
| **AI 生成前端代碼 (30%)** | 提供 Swagger JSON 給 AI，成功生成前端 API Service 模組與 TypeScript/JS Interface。 | 讓 AI 生成前端 UI 元件，但手動修正了大量 API 網址或欄位名稱。 | 生成的前端代碼與後端 API 欄位不匹配，未能給予 AI 足夠的 Context。 | 前端代碼完全手寫，未展現 AI 賦能效率。 |
| **UI/UX 互動品質 (20%)** | 表單具備前端驗證、列表支援動態更新、彈窗提示體驗良好。 | 功能可用，但 UI 版面錯位或無資料時缺少空狀態顯示。 | 表單送出後不會自動重新整理列表，體驗較差。 | UI 畫面破損，按鈕無反應。 |
| **元件結構 (10%)** | 前端元件拆分合理（如 View / Component / Service 隔離）。 | 元件有拆分，但部分單一檔案超過 500 行。 | 所有 UI 與 API 請求全塞在 App.vue 或 App.jsx 中。 | 前端檔案結構混亂。 |

* **交付物**：GitHub 儲存庫（含 Dockerfile）、AI Code Review 報告與重構紀錄 (review\_report.md)。

| 評分項目 | 優秀 (90-100分) | 良好 (75-89分) | 需改進 (60-74分) | 不合格 (\<60分) |
