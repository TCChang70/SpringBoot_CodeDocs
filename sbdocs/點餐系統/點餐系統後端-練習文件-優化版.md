# 1. 系統情境與需求

## 1.1 業務背景

一家餐廳推出**線上點餐系統**。顧客瀏覽菜單 → 選擇項目與數量 → 成立訂單。

- 菜單項目分成不同**分類**（主餐 / 飲料 / 點心）。
- 每個項目可設定**今日是否供應**（is_available）。
- 每個項目有**當日庫存**（stock_quantity）。
- 顧客點餐時，系統要：**扣庫存 + 計算總價 + 建立訂單**，整個流程必須是**一個交易**（全部成功或全部失敗）。
- 員工需要**儀表板**看到：熱賣排行、今日營業額、待處理訂單數。

## 1.2 需求規格表

| 編號 | 功能 | 說明 | 層 |
|------|------|------|-----|
| FR-01-01 | 菜單 CRUD | 新增/查詢/編輯/刪除菜單項目 | Service/Controller |
| FR-01-02 | 菜單篩選 | 依分類、供應狀態查詢 | Repository |
| FR-01-03 | 菜單關鍵字搜尋 | 依名稱模糊搜尋（不分大小寫） | Repository |
| FR-02-01 | 建立訂單 | 一張訂單含多筆明細，**同一交易**扣庫存+算總價 | Service |
| FR-02-02 | 訂單查詢 | 依狀態（PENDING/COMPLETED/CANCELLED）篩選 | Repository |
| FR-03-01 | 儀表板統計 | 熱賣排行、今日營業額、待處理訂單數 | Repository |
| FR-03-02 | 售罄清單 | 列出庫存為 0 的菜單項目 | Repository |

## 1.3 ER 圖

```

─────────────────         ────────────────────     ───────────────────────
```

## 7.2 OrderService（核心）

> 💡 **優化討論題**：原版在 `@Transactional` 方法內對 managed entity 呼叫 `menuRepo.save(menu)` 是否必要？
> JPA 的 **Dirty Checking** 機制會在 commit 時自動偵測並更新變更的欄位，不需手動 `save()`。
> 優化版已移除多餘的 `save()`——請思考：移除後庫存還能正確扣除嗎？為什麼？

```java
@Service
public class OrderService {

    private final OrderRepository    orderRepo;
    private final MenuItemRepository menuRepo;

    public OrderService(OrderRepository orderRepo, MenuItemRepository menuRepo) {
        this.orderRepo = orderRepo;
        this.menuRepo  = menuRepo;
    }

    @Transactional
    public Order createOrder(CreateOrderRequest req) {
        Order order = new Order();
        order.setCustomerName(req.getCustomerName());
        order.setOrderTime(LocalDateTime.now());
        order.setStatus("PENDING");

        BigDecimal total = BigDecimal.ZERO;

        for (CreateOrderRequest.OrderItemRequest itemReq : req.getItems()) {
            MenuItem menu = menuRepo.findById(itemReq.getMenuItemId())
                    .orElseThrow(() -> new ResourceNotFoundException(
                            "Menu item not found: " + itemReq.getMenuItemId()));

            // [A] 停售 → 丟 ItemUnavailableException（語意比 StockNotEnoughException 更精確）
            if (!menu.isAvailable()) {
                throw new [A]________("已停售: " + menu.getName());
            }
            // [B] 庫存不足 → 丟 OutOfStockException
            if (menu.getStockQuantity() < itemReq.getQuantity()) {
                throw new [B]________("庫存不足: " + menu.getName()
                        + " (剩 " + menu.getStockQuantity() + ")");
            }

            // 扣庫存（Dirty Checking 自動 UPDATE，無需 menuRepo.save）
            menu.setStockQuantity(menu.getStockQuantity() - itemReq.getQuantity());

            OrderItem oi = new OrderItem();
            oi.setMenuItem(menu);
            oi.setQuantity(itemReq.getQuantity());
            oi.setUnitPrice(menu.getPrice());
            order.addItem(oi);

            total = total.add(oi.getSubtotal());
        }

        order.setTotalAmount(total);
        return orderRepo.save(order);
    }

    @Transactional(readOnly = true) public List<Order> findAll()                    { return orderRepo.findAll(); }
    @Transactional(readOnly = true) public List<Order> findByStatus(String status)  { return orderRepo.findByStatus(status); }
```

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<Map<String, Object>> handleNotFound(ResourceNotFoundException ex) {
        return buildError(HttpStatus.NOT_FOUND, "NOT_FOUND", ex.getMessage());
    }

    @ExceptionHandler(OutOfStockException.class)
    public ResponseEntity<Map<String, Object>> handleStock(OutOfStockException ex) {
        return buildError(HttpStatus.BAD_REQUEST, "STOCK_NOT_ENOUGH", ex.getMessage());
    }

    // 優化版新增：停售獨立 errorCode
    @ExceptionHandler(ItemUnavailableException.class)
    public ResponseEntity<Map<String, Object>> handleUnavailable(ItemUnavailableException ex) {
        return buildError(HttpStatus.BAD_REQUEST, "ITEM_UNAVAILABLE", ex.getMessage());
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<Map<String, Object>> handleBadRequest(IllegalArgumentException ex) {
        return buildError(HttpStatus.BAD_REQUEST, "BAD_REQUEST", ex.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Map<String, Object>> handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> fieldErrors = new HashMap<>();
        ex.getBindingResult().getFieldErrors()
          .forEach(fe -> fieldErrors.put(fe.getField(), fe.getDefaultMessage()));
        Map<String, Object> body = new HashMap<>();
        body.put("success", false);
        body.put("errorCode", "VALIDATION_ERROR");
        body.put("errors", fieldErrors);
        return ResponseEntity.badRequest().body(body);
    }

    private ResponseEntity<Map<String, Object>> buildError(
            HttpStatus status, String errorCode, String message) {
        Map<String, Object> body = new HashMap<>();
        body.put("success", false);
        body.put("errorCode", errorCode);
        body.put("message", message);
        return ResponseEntity.status(status).body(body);
    }
}
```

## 各差異詳細說明

### 差異 1：帳密安全性

**原版**：
```properties
spring.datasource.username=⑤ ________
spring.datasource.password=⑥ ________
```
暗示直接填入帳密字串。若學生把答案提交 Git，帳密即外洩（屬 OWASP A02 敏感資料暴露）。

**優化版**：
```properties
spring.datasource.username=${DB_USERNAME:root}
spring.datasource.password=${DB_PASSWORD:}
```
`${ENV_VAR:default}` 語法：環境變數未設定時使用預設值，練習環境方便、正式環境安全。
啟動方式：`DB_USERNAME=root DB_PASSWORD=secret mvn spring-boot:run`

---

### 差異 2：CORS allowCredentials 與 allowedHeaders 衝突

**原版問題**：提示「放行所有 headers」引導填入 `"*"`，但：
```
若 allowCredentials=true，則 allowedOrigins / allowedHeaders 不可用 "*"
→ Spring 會拋出 IllegalArgumentException
→ 瀏覽器也會因 CORS 預檢失敗而拒絕請求
```

**優化版**：移除洩漏答案的提示，改為題目外說明，要求明確填入需要的 headers：
```java
config.setAllowedHeaders(List.of("Content-Type", "Authorization", "X-Requested-With"));
```

---

### 差異 3：updateStatus 缺乏輸入驗證

**原版**：
```java
public Order updateStatus(Long id, String status) {
    Order o = findById(id);
    o.setStatus(status);     // 任意字串都能寫進 DB
    return orderRepo.save(o);
}
```
攻擊者可傳入 `"HACKED"` 或超長字串，導致資料異常。

**優化版**：
```java
if (!List.of("PENDING", "COMPLETED", "CANCELLED").contains(newStatus)) {
    throw new IllegalArgumentException("無效的狀態值: " + newStatus);
}
```
GlobalExceptionHandler 已有 `IllegalArgumentException` 的 handler，會回傳 `400 BAD_REQUEST`。

---

### 差異 4：例外語意拆分

**原版**：
```java
// 兩種不同情況都丟同一個例外 → 前端只看到 STOCK_NOT_ENOUGH
throw new StockNotEnoughException("已停售: " + menu.getName());
throw new StockNotEnoughException("庫存不足: " + menu.getName() + " ...");
```

**優化版**：
```
停售 → ItemUnavailableException → errorCode: ITEM_UNAVAILABLE
庫存不足 → OutOfStockException → errorCode: STOCK_NOT_ENOUGH
```
前端可根據 `errorCode` 顯示不同提示（例：「此商品今日不提供」vs.「庫存不足，請減少數量」）。

---

### 差異 5：JPA Dirty Checking（多餘的 save）

**原版**：
```java
menu.setStockQuantity(menu.getStockQuantity() - itemReq.getQuantity());
menuRepo.save(menu);   // ← 多餘
```

在 `@Transactional` 方法內，從 DB 載入的 entity 處於 **managed（受管理）** 狀態。
JPA 的 **Dirty Checking** 機制會在交易 commit 時，自動比較快照與當前值，只要有變更就發出 `UPDATE`。
**因此不需要手動呼叫 `save()`**，多呼叫只是浪費資源（會觸發額外的 SQL）。

移除後庫存仍能正確扣除，因為 Dirty Checking 會在 `orderRepo.save(order)` 之後的 commit 時統一寫入。
