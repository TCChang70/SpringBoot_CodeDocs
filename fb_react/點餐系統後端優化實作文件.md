## 1. 專案簡介與優化總覽

### 1.1 系統目標（與規劃書對齊）

規劃書最終版的目標是一套完整的餐廳點餐系統，本文件優化後的後端涵蓋：

| 功能 | 說明 |
| --- | --- |
| 使用者註冊 / 登入 | 取得 JWT Token，之後所有 API 呼叫附上 `Authorization: Bearer <token>` |
| 菜單瀏覽 | 公開查詢菜單（不需要登入） |
| 送出訂單 | 登入後可選擇餐點送出訂單，**價格由後端計算** |
| 查詢個人訂單 | 只能分頁查詢「自己的」歷史訂單 |
| 修改 / 取消訂單 | 只能編輯「自己」且「尚未確認」的訂單 |
| 後台訂單管理 | 管理員（ADMIN）可查詢所有人訂單、改狀態、刪除訂單 |
| 後台菜單維護 | 管理員可批次調整菜單價格（示範 `@Modifying` 批次更新） |
| API 文件 | Swagger UI（OpenAPI 3），可直接在瀏覽器測試所有 API |

### 1.2 原始後端程式碼問題盤點（優化動機）

規劃書中的後端程式碼（`Order` / `OrderItem` / `OrderRepository` / `OrderController` 與後續 PUT/DELETE 擴充）共盤點出 **22 個問題**，依「資料層 → 安全層 → 架構層」分類如下，每一項都會在本文件後續章節給出對應實作。

#### 1.2.1 資料層（Entity / 資料庫）

| # | 原始作法 | 問題與風險 | 優化後作法 |
| --- | --- | --- | --- |
| 1 | `@Entity class Order` 未指定 `@Table` | 資料表名稱會是 `order`，但 **ORDER 是 SQL 保留字**，Hibernate 產生的 `create table order ...` 在 MySQL 直接語法錯誤，**應用程式啟動即失敗** | `@Table(name = "orders")`（陷阱詳見 5.5） |
| 2 | `@OneToMany(cascade = CascadeType.ALL)` 無 `mappedBy` / `@JoinColumn` | Hibernate 預設建立**第三張中間表**（如 `orders_order_items`）：多一張表、查詢多一次 JOIN、更新順序難控制 | 改為**雙向關聯**：`OrderItem` 端 `@ManyToOne + @JoinColumn(name = "order_id")`，`Order` 端 `mappedBy = "order"` |
| 3 | 關聯無 `orphanRemoval` | 「修改訂單」把整包 items 換掉後，舊明細留在資料庫成孤兒資料，長期膨脹 | `orphanRemoval = true` + `replaceItems()` 領域方法（詳見 5.5、7.3） |
| 4 | `OrderItem` 只有 `name`、`price` | 前端明明送了 `quantity`，資料庫卻存不下——點 3 碗牛肉麵只能存 1 筆，**資料遺失** | 新增 `quantity` 欄位（`int`，不可為負） |
| 5 | 價格用 `int` | 金額運算有精度風險，也無法表達小數 | `BigDecimal` + 資料表 `DECIMAL(10,2)` |
| 6 | 進階版規劃把 items 存成 `TEXT` 字串（如「牛肉麵,珍奶」） | 無法對品項查詢、統計、驗算總價；違反資料庫正規化 | 正規化為 `order_items` 資料表 |
| 7 | 無建立時間、訂單狀態、版本欄位 | 無法排序最新訂單、無法限制「尚未出餐才能改」、併發同改互相覆寫 | 新增 `created_at`、`status`、`@Version` 樂觀鎖（詳見 7.6） |
| 8 | 沒有 `menu_items` 資料表 | 價格只存在前端 JavaScript，後端無「價格的單一真相」 | 新增 `menu_items` 表，下單價格一律後端查表（詳見 5.4、7.3） |

> ⚠️ **最關鍵的一個坑（#1）**：實體類別名稱 `Order` 對應的預設資料表名就是 `order`。`ORDER BY` 的 `ORDER` 是 SQL 保留字，MySQL 建表會直接失敗。這是新手把規劃書程式碼貼進專案後「**為什麼啟動就爆紅**」的第一個原因。

#### 1.2.2 安全層

| # | 原始作法 | 問題與風險 | 優化後作法 |
| --- | --- | --- | --- |
| 9 | 前端傳來的 `price` 直接存進資料庫 | **重大漏洞**：任何人用瀏覽器開發者工具改一下 request，就能 1 元買牛肉麵 | 請求 DTO 只收 `menuItemId + quantity`，價格一律後端查 `menu_items` 計算（詳見 7.3） |
| 10 | `@CrossOrigin(origins = "*")` | 任何網站都能跨域呼叫此 API | CORS 白名單，來源由設定檔控制（詳見 8.5） |
| 11 | `updateOrder` / `deleteOrder` 無身分驗證 | **任何人可改、可刪任何人的訂單**（規劃書後續已意識到此問題並規劃 JWT） | JWT 驗證 + 訂單擁有權檢查；查無權限統一回 404 避免探測（詳見 7.3） |
| 12 | 密碼欄位規劃為明文儲存 | 資料庫一旦外洩，所有帳號密碼直接曝光 | BCrypt 雜湊儲存（不可逆，加鹽）（詳見 7.2） |
| 13 | 無任何輸入驗證 | `quantity` 可以是 0 或 -5、名稱可以空白，髒資料直接進資料庫 | Request DTO + Bean Validation（`@Valid`、`@Min`、`@Max`…）（詳見 9.2） |
| 14 | JWT 金鑰與效期沒有規劃管理方式 | 金鑰硬編碼難以輪替、效期太長提高盜用風險 | `app.jwt.*` 設定項 + 環境變數覆寫、效期 1 小時（詳見 4、8.2） |

#### 1.2.3 架構層

| # | 原始作法 | 問題與風險 | 優化後作法 |
| --- | --- | --- | --- |
| 15 | Controller 直接注入 Repository | 沒有 Service 層 → 沒有交易邊界；計價、狀態檢查等商業邏輯無處安放 | Controller → Service → Repository 三層（詳見 7.1） |
| 16 | `@Autowired` 欄位注入 | 不利單元測試、隱藏依賴關係、無法宣告 final | 建構子注入（Lombok `@RequiredArgsConstructor`） |
| 17 | 直接回傳 Entity 或 `Map<String, Object>` | 型別不明；LAZY 關聯序列化地雷；**內部欄位（如密碼雜湊）可能整包外洩** | 型別安全的 Request / Response DTO（Java record）（詳見 9.1） |
| 18 | `getAllOrders()` 回傳全部訂單，無分頁 | 訂單一多，單次查詢把整張表撈進記憶體，效能崩潰 | `Pageable` 分頁 + 回傳分頁 DTO（詳見 9.2） |
| 19 | 訂單明細 LAZY 載入、逐筆觸發查詢 | N+1 查詢問題：1 頁 20 筆訂單明細 = 21 次 SQL | `JOIN FETCH` 一次抓齊（詳見 6.4） |
| 20 | 無例外處理機制 | 驗證失敗、查無資料全變成 HTTP 500，stack trace 直接回給前端 | `@RestControllerAdvice` 統一錯誤格式與狀態碼（詳見 9.8） |
| 21 | `ddl-auto=update` 一路用到底 | 正式環境 schema 會漂移、無法版本控管 | 開發期 `create-drop`/`update`；正式環境建議 Flyway 遷移 + `validate`（詳見 4.3、10.3） |
| 22 | 依賴 `spring-boot-starter-web`（舊名） | Spring Boot 4 起已改名，舊名已標記為過時 | 升級為 `spring-boot-starter-webmvc`（詳見 3.2） |

### 1.3 優化設計原則

後續所有實作都遵循以下五個原則，遇到取捨時以此為準：

1. **單一真相（Single Source of Truth）**：菜色價格只存在 `menu_items` 資料表；訂單總價由 Entity 的領域方法計算，不靠前端。
2. **絕不信任前端（Never Trust the Client）**：前端送來的任何價格、金額、身分資訊都不直接採信；身分以 JWT 簽章驗證。
3. **分層清楚（Layered Architecture）**：Controller 只做協調、Service 承載商業邏輯與交易、Repository 只負責存取。
4. **最小揭露（Least Exposure）**：別人的訂單查詢回 404 而非 403；錯誤訊息不洩漏內部細節；Entity 不直接外拋。
5. **可驗證（Testable & Verifiable）**：建構子注入、DTO 邊界清楚、Swagger UI 可逐一支測，附練習題驗收。

### 1.5 優化前後架構對照

**原始（規劃書）架構：**

```
前端 jQuery ──► OrderController ──► OrderRepository ──► MySQL
                （直接注入、無交易、        （orders + 不明確的關聯表）
                 無驗證、回傳 Map）
```

**優化後架構：**

```
前端 (jQuery/任何客户端)
   │  HTTP + JSON ＋ Authorization: Bearer <JWT>
   ▼
JwtAuthFilter ──► SecurityConfig（JWT 驗證、CORS 白名單、角色控管 RBAC）
   ▼
Controller 層（@Valid 驗證請求 DTO → 呼叫 Service → 包裝回應 DTO 與狀態碼）
   ▼
Service 層（商業邏輯：計價、擁有權、狀態規則；@Transactional 交易邊界）
   ▼
Repository 層（Spring Data JPA；Derived Query / JPQL / JOIN FETCH / 分頁）
   ▼
MySQL（users / menu_items / orders / order_items ＋ 外鍵與索引）
```

> 兩者最大的差別：**原始版把「存取」直接暴露給 HTTP 層**；優化版在兩者之間補上了「驗證（Security）」與「商業規則（Service）」兩道牆。

> ```bash

> ```
> 建完後記得在 `application.properties` 把密碼設成 `root123`。

### 2.2 建立資料庫

先以 root（或其他有建庫權限的帳號）連線 MySQL，執行：

```sql
-- utf8mb4：完整支援中文與 emoji；排序規則用 unicode_ci（不分大小寫比較）
CREATE DATABASE restaurant
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

> ⚠️ **一定要用 utf8mb4**。若用預設 latin1，中文菜名（如「牛肉麵」）會存成問號。utf8（utf8mb3）在 MySQL 是閹割版，官方建議一律 utf8mb4。

### 2.3 資料庫帳號建議（可選）

開發期直接用 root 即可；若要照正式做法，可建立專用帳號：

```sql
CREATE USER 'restaurant'@'localhost' IDENTIFIED BY '你的密碼';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES
  ON restaurant.* TO 'restaurant'@'localhost';
FLUSH PRIVILEGES;
```

### 4.2 逐項說明

| 屬性 | 意義 |
| --- | --- |
| `spring.datasource.url` | 連線字串。`useSSL=false` 本機開發免憑證；`serverTimezone=Asia/Taipei` 避免時區警告；`characterEncoding=utf8` 確保中文不亂碼；`allowPublicKeyRetrieval=true` 搭配 MySQL 8 預設的 `caching_sha2_password` 在無 TLS 時也能取得公鑰 |
| `hikari.*` | 連線池上限 10、最小閒置 2、取得連線最長等 30 秒。連線池是「DB 連線很貴（TCP 交握 + 驗證）→ 借還重用」的優化 |
| `spring.jpa.hibernate.ddl-auto` | 見 4.3 對照表 |
| `spring.jpa.show-sql` / `format_sql` | 開發期把 SQL 印到 console，方便觀察 N+1 與 JOIN FETCH 效果 |
| `spring.jpa.open-in-view` | **設 false（重要優化）**：見下方 ⚠️ |
| `spring.sql.init.defer-datasource-initialization` | 讓 `data.sql` 等 Hibernate 建完表**之後**才執行（否則表還不存在就 INSERT 會失敗） |
| `spring.sql.init.encoding=UTF-8` | data.sql 內有中文菜名，必須明確指定編碼（否則在 Windows 預設編碼下可能亂碼） |
| `spring.data.web.pageable.max-page-size` | 分頁 size 上限，擋住異常大的請求 |
| `app.jwt.secret` | HS256 金鑰，**至少 32 bytes**；`${JWT_SECRET:預設值}` 語法＝「有環境變數用環境變數，否則用預設」 |
| `app.jwt.expiration-ms` | Token 效期 3600000ms = 1 小時 |
| `app.cors.allowed-origins` | 允許跨域呼叫的前端來源清單（5500 是 VS Code Live Server、63342 是 IntelliJ 內建預覽），部署時換成正式網域 |

> ⚠️ **`spring.jpa.open-in-view=false` 是什麼？**
> 預設 `true` 時，Spring 會把「資料庫連線 + Hibernate Session」一路抱到 HTTP 回應寫完為止（渲染 view / 序列化 JSON），期間 LAZY 關聯隨時可再查——方便，但缺點是：(1) 連線被佔用更久，連線池容易耗盡；(2) 效能問題被「延期」到序列化階段才爆 N+1，難察覺；(3) 交易邊界模糊。設成 `false` 後，**LAZY 存取只能發生在 Service 的 `@Transactional` 範圍內**，逼我們把查詢收在正確的分層——本文件所有 DTO 組裝都在 Service 內完成，正是配合這個設定。

### 4.3 `ddl-auto` 四種模式怎麼選

| 模式 | 行為 | 適用時機 |
| --- | --- | --- |
| `create-drop` | 啟動建表、關閉刪表（資料每次清空） | 教學、單元測試。**本文件用它**：配合 data.sql 每次重建種子資料，永遠乾淨 |
| `update` | 有表就比對欄位差異微調，沒表就建 | 原型開發。缺點：欄位改名/刪除不會處理，schema 會慢慢漂移 |
| `validate` | 只檢查 Entity 與資料表是否一致，不一致就啟動失敗 | 正式環境搭配「受控的建表方式」（Flyway/Liquibase） |
| `none` | 完全不管 schema | 正式環境，schema 完全交給遷移工具 |

> ⚠️ 規劃書直接使用 `update`。本文件建議：**開發期** `create-drop`（重置乾淨）→ **正式環境** 改用 Flyway 管理 SQL 遷移腳本 + `ddl-auto=validate`，schema 進版本控制、可審查、可回滚。這已是業界標準做法。

## 5. 實體設計（Entity）

### 5.1 資料表關聯總覽

```
users (使用者)                 menu_items (菜單品項)
  id  BIGINT PK                  id  BIGINT PK
  username  UNIQUE               name / price / image_url / available
  password  (BCrypt 雜湊)
  role     (USER / ADMIN)
        │                              │
        │ 1                            │ 1
        │                              │
        ▼ N                            ▼ N
orders (訂單) ──── 1 ────► order_items (訂單明細)
  id  PK                       id  PK
  user_id  FK → users.id       order_id  FK → orders.id
  status   (PENDING/…)         menu_item_id  FK → menu_items.id
  total_amount DECIMAL(10,2)   item_name / unit_price   ← 下單當時快照
  version  (樂觀鎖)             quantity INT
  created_at / updated_at
```

**關聯摘要：**

- `users 1 ── N orders`（一位使用者多筆訂單）
- `orders 1 ── N order_items`（一筆訂單多筆明細）
- `menu_items 1 ── N order_items`（一個品項出現在多筆明細；明細另存**名稱與單價快照**）

> 💡 **為什麼明細要存快照（item_name / unit_price）？**
> 菜單改價後，歷史訂單不能跟著變——去年賣 100 元的雞排飯，訂單裡永遠要是 100 元。快照欄位讓「菜單」與「訂單」各自獨立演化，同時保留關聯可查。這是電商/訂單系統的標準模式。

### 5.3 User（使用者）

```java
// src/main/java/com/restaurant/ordersystem/entity/User.java
package com.restaurant.ordersystem.entity;

import jakarta.persistence.*;
import lombok.Getter;
import lombok.Setter;

import java.time.LocalDateTime;
import java.util.Objects;

@Entity
@Table(name = "users",
      uniqueConstraints = @UniqueConstraint(name = "uk_users_username",
                                            columnNames = "username"))
@Getter
@Setter
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 50)
    private String username;

    /** BCrypt 雜湊後的密碼（絕不存明文） */
    @Column(nullable = false)
    private String password;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private Role role;

    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    /** JPA 規範：Entity 需要無參數建構子（protected 即可，防止外部直接 new） */
    protected User() {
    }

    /** 業務上唯一合法的建構入口：必傳雜湊後的密碼 */
    public User(String username, String encodedPassword, Role role) {
        this.username = username;
        this.password = encodedPassword;
        this.role = role;
    }

    @PrePersist
    void onCreate() {
        if (this.createdAt == null) {
            this.createdAt = LocalDateTime.now();
        }
    }

    // ---- equals/hashCode：以 id 為準（同一列資料 = 同一物件語意） ----
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User other)) return false;
        return this.id != null && this.id.equals(other.id);
    }

    @Override
    public int hashCode() {
        // 用固定值而非 id：物件尚未存入資料庫（id 為 null）時，hashCode 不能變，
        // 否則放入 HashSet 後再 save，會「找不到」自己
        return getClass().hashCode();
    }
}
```

**逐段講解：**

- `@Table(name = "users")`：明確命名（MySQL 也把 `users` 當關鍵字處理較安全）；`uniqueConstraints` 在**資料庫層**保證帳號唯一——就算 Service 忘記檢查重複，INSERT 也會被資料庫擋下（雙保險）。
- `password` 存 BCrypt 雜湊（約 60 字元，故不設長度限制）。
- `@PrePersist`：JPA 生命週期回呼，第一次存入前自動補建立時間——不依賴呼叫者記得設定。
- 建構子只暴露「必填齊全」的版本，避免 new 出缺 role 的半成品使用者。

> ⚠️ **equals/hashCode 陷阱**：直接用 `Objects.hash(id)` 時，未存入的 Entity（id = null）hash 值與存入後不同——放進 `HashSet` 再 save 就找不到了。業界慣用「`equals` 比id、`hashCode` 回固定值」這個組合。另外**絕對不要**在雙向關聯的 Entity 上用 Lombok 的 `@EqualsAndHashCode` / `@ToString`（會碰觸 LAZY 關聯，輕則多一堆查詢、重則 `LazyInitializationException` 或無窮遞迴）。

### 5.5 Order（訂單）— 本專案的核心 Entity

```java
// src/main/java/com/restaurant/ordersystem/entity/Order.java
package com.restaurant.ordersystem.entity;

import jakarta.persistence.*;
import lombok.Getter;
import lombok.Setter;

import java.math.BigDecimal;
import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "orders")   // ⚠️ 不可省：order 是 SQL 保留字
@Getter
@Setter
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    /** 訂單屬於誰：多對一，LAZY + FK 欄位 user_id */
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_id", nullable = false)
    private User user;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private OrderStatus status = OrderStatus.PENDING;

    /** 總金額：由本類別的 recalculateTotal() 維護，不假設前端會算 */
    @Column(name = "total_amount", nullable = false, precision = 10, scale = 2)
    private BigDecimal totalAmount = BigDecimal.ZERO;

    /**
     * 一筆訂單有多筆明細。
     * mappedBy = "order"：關聯由 OrderItem 端的 order 欄位持有（雙向關聯）。
     * cascade = ALL：存訂單時連同明細一起存。
     * orphanRemoval = true：明細從集合移除後，交易提交時自動 DELETE（避免孤兒資料）。
     */
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    /** 樂觀鎖：併發同改時，後提交者會拋例外（HTTP 409），不會無聲覆寫 */
    @Version
    private Long version;

    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @Column(name = "updated_at")
    private LocalDateTime updatedAt;

    protected Order() {
    }

    public Order(User user) {
        this.user = user;
    }

    @PrePersist
    void onCreate() {
        this.createdAt = LocalDateTime.now();
        if (this.status == null) this.status = OrderStatus.PENDING;
        recalculateTotal();
    }

    @PreUpdate
    void onUpdate() {
        this.updatedAt = LocalDateTime.now();
        recalculateTotal();
    }

    // ================= 領域方法：把商業規則封進 Entity =================

    /** 加入一筆明細（雙向關聯兩邊都要設定） */
    public void addItem(OrderItem item) {
        items.add(item);
        item.setOrder(this);
        recalculateTotal();
    }

    /** 整批換掉明細（orphanRemoval 會在提交時刪除舊資料） */
    public void replaceItems(List<OrderItem> newItems) {
        for (OrderItem old : new ArrayList<>(items)) {
            old.setOrder(null);
        }
        items.clear();
        newItems.forEach(this::addItem);
    }

    /** 依明細重算總價（價格快照 × 數量） */
    public void recalculateTotal() {
        this.totalAmount = items.stream()
                .map(OrderItem::getSubtotal)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }

    /** 只有「待處理」的訂單能修改/取消（對應規劃書「尚未出餐才可編輯」） */
    public boolean isEditable() {
        return status == OrderStatus.PENDING;
    }
}
```

**逐段講解（對照原始程式碼的改進）：**

| 原始程式碼 | 優化後 | 說明 |
| --- | --- | --- |
| （無 `@Table`） | `@Table(name = "orders")` | `order` 是保留字，`orders` 才能正常建表 |
| `@OneToMany(cascade = ALL)`（無 mappedBy） | `mappedBy = "order"` + `orphanRemoval = true` | 不再產生第三張中間表；改訂單時舊明細自動刪除 |
| （明細無 order 欄位） | `OrderItem` 端 `@ManyToOne + @JoinColumn(name="order_id")` | 真正的 FK 在明細表上，雙向導覽 |
| （無總價欄位） | `total_amount DECIMAL(10,2)` + `recalculateTotal()` | 總價由後端算，可排序、可統計、可對帳 |
| （無狀態） | `status` + `isEditable()` | 「尚未出餐才能改」的規則有了實作基礎 |
| （無版本） | `@Version` | 樂觀鎖，防併發覆寫（示範見 7.6、11.5） |

**三個關鍵註解深入說明：**

1. **`mappedBy` 與雙向關聯**：關聯的「擁有者（owning side）」是 `OrderItem.order` 這個 FK 欄位；`Order.items` 只是「鏡像」。新增/刪除時務必兩邊同步（`addItem()` 一次設好兩邊），否則記憶體與資料庫不一致——這是 `addItem()` 領域方法存在的目的。
2. **`orphanRemoval`**：把明細從 `items` 移除並提交後，Hibernate 自動 `DELETE FROM order_items WHERE id=?`。沒有它的話，原始的「`order.setItems(新清單)`」只會 INSERT 新明細，舊的永遠留在庫裡（問題 #3）。
3. **`@Version`**：Hibernate 更新時自動加上 `WHERE version = 舊值`；有人先改過 → 影響列數 0 → 拋 `ObjectOptimisticLockingFailureException` → 我們在 9.8 轉成 HTTP 409，讓前端知道「請重新整理再試」。

### 5.6 OrderItem（訂單明細）— 含價格快照

```java
// src/main/java/com/restaurant/ordersystem/entity/OrderItem.java
package com.restaurant.ordersystem.entity;

import jakarta.persistence.*;
import lombok.Getter;
import lombok.Setter;

import java.math.BigDecimal;
import java.util.Objects;

@Entity
@Table(name = "order_items")
@Getter
@Setter
public class OrderItem {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    /** 明細屬於哪筆訂單：FK order_id（雙向關聯的擁有方） */
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private Order order;

    /** 點的是哪個菜單品項：FK menu_item_id */
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "menu_item_id", nullable = false)
    private MenuItem menuItem;

    /** 下單當時的品項名稱快照（菜單改名不影響歷史訂單） */
    @Column(name = "item_name", nullable = false, length = 100)
    private String itemName;

    /** 下單當時的單價快照（菜單改價不影響歷史訂單） */
    @Column(name = "unit_price", nullable = false, precision = 10, scale = 2)
    private BigDecimal unitPrice;

    /** 數量：規則 1～99，由 DTO 驗證保證 */
    @Column(nullable = false)
    private int quantity;

    protected OrderItem() {
    }

    /** 建立明細時自動從菜單品項「拍照存證」 */
    public OrderItem(MenuItem menuItem, int quantity) {
        this.menuItem = menuItem;
        this.itemName = menuItem.getName();
        this.unitPrice = menuItem.getPrice();
        this.quantity = quantity;
    }

    /** 小計 = 單價 × 數量（BigDecimal 相乘） */
    public BigDecimal getSubtotal() {
        return unitPrice.multiply(BigDecimal.valueOf(quantity));
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof OrderItem other)) return false;
        return this.id != null && this.id.equals(other.id);
    }

    @Override
    public int hashCode() {
        return getClass().hashCode();
    }
}
```

**逐段講解：**

- 建構子從 `MenuItem` **拷貝**名稱與價格 → 快照。查歷史訂單時連 `menu_items` 都不用 JOIN（省查詢），且天然免疫「菜單事後改動」。
- `getSubtotal()` 用 `BigDecimal.multiply`：金額運算一律 BigDecimal，不用 double（0.1 + 0.2 ≠ 0.3 的二進位誤差）。

### 5.7 Lombok 使用規則（本專案）

| 註解 | 產生 | 用在 |
| --- | --- | --- |
| `@Getter` / `@Setter` | 所有欄位的 getter/setter | Entity、BusinessException |
| `@RequiredArgsConstructor` | 以 **final 欄位**為參數的建構子（＝建構子注入） | Service、Controller、Filter |
| `@Slf4j` | `private static final Logger log` | GlobalExceptionHandler |

> ⚠️ **三不用**：Entity 上不用 `@ToString`（雙向關聯遞迴＋LAZY 載入地雷）、不用 `@EqualsAndHashCode`（同上）、不用 `@Data`（＝Getter+Setter+ToString+EqualsHashCode+…，等於前兩個坑全踩）。這是 JPA + Lombok 最常見的翻車點。

## 6. Repository 層

### 6.1 Spring Data JPA 內建方法（不用寫就有）

宣告 `interface XxxRepository extends JpaRepository<Entity, Long>` 後，直接可用：

| 方法 | 對應 SQL 概念 | 本專案用途 |
| --- | --- | --- |
| `save(entity)` | INSERT / UPDATE | 建立訂單、改狀態 |
| `findById(id)` | `WHERE id = ?` | 查單筆 |
| `findAll(pageable)` | `LIMIT/OFFSET` | 後台分頁列表 |
| `findAllById(ids)` | `WHERE id IN (...)` | 下單時一次查多個品項（避免 N+1） |
| `existsById(id)` / `count()` | EXISTS / COUNT | 刪除前存在檢查、統計 |
| `deleteById(id)` | DELETE | 刪除訂單（明細由 cascade 帶走） |

### 6.2 UserRepository — Derived Query 入門

```java
// src/main/java/com/restaurant/ordersystem/repository/UserRepository.java
package com.restaurant.ordersystem.repository;

import com.restaurant.ordersystem.entity.User;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.Optional;

public interface UserRepository extends JpaRepository<User, Long> {

    // Derived Query：方法名即查詢。Spring Data 依命名規則自動生成
    // SELECT * FROM users WHERE username = ?
    Optional<User> findByUsername(String username);

    // SELECT COUNT(*) FROM users WHERE username = ? > 0
    boolean existsByUsername(String username);
}
```

**重點說明：Derived Query（衍生查詢）**

- 語法：`findBy + 屬性名 + 條件關鍵字`。常用關鍵字：`Is`/`Equals`（省略）、`Containing`（LIKE %x%）、`IgnoreCase`、`True/False`、`LessThan/GreaterThan`、`Between`、`OrderBy_屬性_Asc/Desc`。
- 回傳型別決定行為：`Optional<T>`（最多一筆）、`List<T>`、`boolean`、`long`、`Page<T>`（搭配參數 `Pageable`）。
- **對應端點**：`findByUsername` → `POST /api/auth/login`（登入查人）；`existsByUsername` → `POST /api/auth/register`（檢查重複）。

### 6.3 MenuItemRepository — Derived Query 進階 + `@Modifying` 批次更新

```java
// src/main/java/com/restaurant/ordersystem/repository/MenuItemRepository.java
package com.restaurant.ordersystem.repository;

import com.restaurant.ordersystem.entity.MenuItem;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Modifying;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.math.BigDecimal;
import java.util.List;

public interface MenuItemRepository extends JpaRepository<MenuItem, Long> {

    // 1) 布林條件 + 排序：供應中、由便宜到貴
    // SELECT * FROM menu_items WHERE available = true ORDER BY price ASC
    List<MenuItem> findByAvailableTrueOrderByPriceAsc();

    // 2) 模糊搜尋（不分大小寫）：LIKE %keyword%（MySQL utf8mb4_unicode_ci 本身就不分大小寫）
    List<MenuItem> findByNameContainingIgnoreCaseAndAvailableTrue(String keyword);

    // 3) 價格區間條件
    List<MenuItem> findByPriceLessThanAndAvailableTrue(BigDecimal price);

    // 4) @Modifying 批次更新：一次 UPDATE 全部供應中品項的價格
    //    例：全面調漲 5% → factor = 1.05
    @Modifying(clearAutomatically = true)
    @Query("""
           UPDATE MenuItem m
           SET m.price = m.price * :factor
           WHERE m.available = true
           """)
    int adjustPriceByFactor(@Param("factor") BigDecimal factor);
}
```

**重點說明：**

- **`@Modifying`**：宣告「這是 UPDATE/DELETE 而非 SELECT」。沒有它，Spring Data 會把 UPDATE 當查詢執行而拋錯。
- **必須在 `@Transactional` 內呼叫**（本專案在 `MenuService.adjustPrice()`，見 7.4）——JPQL 的 UPDATE 不走 Entity 生命週期，需要交易包住才能 commit。
- **`clearAutomatically = true`**：執行後清空一級快取（persistence context），避免同一個交易裡「剛才查到的舊價格物件」還被拿來用，看到過期資料。
- 回傳 `int` = 影響筆數，直接回報給呼叫者「調整了幾道菜」。
- **對應端點**：1) → `GET /api/menu`；2) → `GET /api/menu/search?keyword=飯`；3) → `GET /api/menu/price-under?price=100`；4) → `PUT /api/admin/menu-items/price-adjustment`。

> ⚠️ **金額捨入**：`m.price * :factor` 的結果由 MySQL 存回 `DECIMAL(10,2)` 時自動四捨五入到小數 2 位（例如 100.00 × 1.05 = 105.0000 → 存 105.00）。若你要明確控制捨入模式（如一律無條件進位），需在 Java 端逐筆處理或改用 SQL 的 `ROUND()`。

### 6.4 OrderRepository — 分頁、JOIN FETCH、聚合統計

先看「未優化前」的自然寫法（示意）：

```java
// V0（示意，有 N+1 問題）：
Page<Order> findByUserId(Long userId, Pageable pageable);
```

它查回一頁訂單沒問題；但之後 Service 若逐筆存取 `order.getUser()`（LAZY），20 筆訂單 = **20 次額外 SELECT**——這就是 N+1。優化版改用 `JOIN FETCH` 一次抓齊：

```java
// src/main/java/com/restaurant/ordersystem/repository/OrderRepository.java
package com.restaurant.ordersystem.repository;

import com.restaurant.ordersystem.entity.Order;
import com.restaurant.ordersystem.entity.OrderStatus;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.List;
import java.util.Optional;

public interface OrderRepository extends JpaRepository<Order, Long> {

    /**
     * 使用者自己的訂單（分頁）。
     * JOIN FETCH o.user：把「多對一」的 user 一次 JOIN 進來，
     * 之後存取 order.getUser() 不再觸發額外查詢。
     */
    @Query("""
           SELECT o FROM Order o
           JOIN FETCH o.user
           WHERE o.user.id = :userId
           """)
    Page<Order> findByUserId(@Param("userId") Long userId, Pageable pageable);

    /** 依狀態過濾的分頁（後台用） */
    @Query("""
           SELECT o FROM Order o
           JOIN FETCH o.user
           WHERE o.status = :status
           """)
    Page<Order> findByStatus(@Param("status") OrderStatus status, Pageable pageable);

    /** 全部訂單（分頁，後台用） */
    @Query("SELECT o FROM Order o JOIN FETCH o.user")
    Page<Order> findAllWithUser(Pageable pageable);

    /**
     * 查單筆 + 明細：JOIN FETCH o.items 解決明細的 N+1。
     * DISTINCT：JOIN 明細會讓訂單列重複，必須去除。
     */
    @Query("""
           SELECT DISTINCT o FROM Order o
           JOIN FETCH o.user
           JOIN FETCH o.items
           WHERE o.id = :id
           """)
    Optional<Order> findByIdWithItems(@Param("id") Long id);

    /** 使用者訂單數（個人頁顯示「共 N 筆」） */
    long countByUserId(Long userId);

    /**
     * 聚合統計：各狀態訂單數。
     * 介面投射（projection）：只抓需要的欄位，不載入整個 Entity。
     */
    @Query("""
           SELECT o.status AS status, COUNT(o) AS count
           FROM Order o
           GROUP BY o.status
           """)
    List<StatusCount> countGroupByStatus();

    /** 投射介面：Spring Data 會為它生成實作，getters 對應 SELECT 別名 */
    interface StatusCount {
        OrderStatus getStatus();
        Long getCount();
    }
}
```

**重點說明：**

| 技巧 | 用在哪 | 效果 |
| --- | --- | --- |
| `@Query` + JPQL | 全部查詢 | JPQL 是「以 Entity 與屬性名撰寫的 SQL」：`SELECT o FROM Order o` 的 `Order` 是**類別名**不是表名 |
| `JOIN FETCH`（To-One） | 三個分頁查詢 | 分頁安全：user 是多對一，JOIN 不會讓列數膨脹 |
| `JOIN FETCH`（To-Many）+ `DISTINCT` | `findByIdWithItems` | 一筆訂單 JOIN 出多列明細 → 列重複 → 必須 `DISTINCT` 去重 |
| `Pageable` 參數 | 分頁查詢 | Spring Data 自動 `LIMIT/OFFSET` 與 `COUNT` |
| 介面投射 | `countGroupByStatus` | 只 SELECT 兩個欄位，不建 Entity 物件 |

**對應端點：**

| Repository 方法 | API 端點 |
| --- | --- |
| `findByUserId` | `GET /api/orders/my` |
| `findAllWithUser` / `findByStatus` | `GET /api/admin/orders`（可選 `?status=`） |
| `findByIdWithItems` | `GET /api/orders/my/{id}`、`GET /api/admin/orders/{id}`、PUT/DELETE 前置查詢 |
| `countByUserId` | 練習題 2 素材 |
| `countGroupByStatus` | `GET /api/admin/orders/stats` |

> ⚠️ **N+1 觀察法**：啟動時 `show-sql=true`。呼叫 `GET /api/orders/my` 時——沒有 `JOIN FETCH o.user` 會看到「1 次 SELECT orders + 每筆 1 次 SELECT users」；有 `JOIN FETCH` 則只有 1 次 JOIN 查詢。到 11.5 會帶你實際比對 log。

> ⚠️ **為什麼分頁查詢不 `JOIN FETCH o.items`？**
> 對「一對多（集合）」做 JOIN FETCH 搭配分頁時，Hibernate 無法在 SQL 層正確 LIMIT（一筆訂單被明細乘成多列，砍列會砍壞資料），只好把**全部結果撈進記憶體再分頁**（log 會出現 `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory`）——資料量大時反而更慢。正解：**列表頁只回摘要（不碰 items）；要明細時打詳情端點 `findByIdWithItems` 一次抓齊**。這也是「列表/詳情分離」API 設計的原因。

## 7. Service 層

### 7.1 為什麼需要 Service 層？

原始程式讓 Controller 直接呼叫 Repository，三個後果：

1. **沒有交易邊界**：`save(order)` + 存明細 + 算總價若分散多步驟，中途失敗會留半套資料。
2. **商業規則無處安放**：「不可點下架品項」「總價後端算」「只能改自己的訂單」寫進 Controller 會又臭又長且無法重用。
3. **無法測試**：要 mock 一堆 Repository 才能測一段邏輯。

Service 層 = **交易邊界 + 商業規則的單一住所**。Controller 薄、Repository 啞、Service 厚。

### 7.2 AuthService — 註冊與登入（BCrypt）

```java
// src/main/java/com/restaurant/ordersystem/service/AuthService.java
package com.restaurant.ordersystem.service;

import com.restaurant.ordersystem.dto.request.LoginRequest;
import com.restaurant.ordersystem.dto.request.RegisterRequest;
import com.restaurant.ordersystem.dto.response.TokenResponse;
import com.restaurant.ordersystem.entity.Role;
import com.restaurant.ordersystem.entity.User;
import com.restaurant.ordersystem.exception.BusinessException;
import com.restaurant.ordersystem.repository.UserRepository;
import com.restaurant.ordersystem.security.JwtService;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@RequiredArgsConstructor
public class AuthService {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;   // 來自 SecurityConfig 的 Bean
    private final JwtService jwtService;

    /** 註冊：帳號唯一檢查 → BCrypt 雜湊 → 存檔 */
    @Transactional
    public User register(RegisterRequest request) {
        if (userRepository.existsByUsername(request.username())) {
            throw new BusinessException(HttpStatus.CONFLICT, "使用者名稱已被註冊");
        }
        User user = new User(
                request.username(),
                passwordEncoder.encode(request.password()),  // 雜湊，絕不存明文
                Role.USER);                                    // 註冊一律是 USER
        return userRepository.save(user);
    }

    /** 登入：查人 → 比對雜湊 → 發 JWT */
    @Transactional(readOnly = true)
    public TokenResponse login(LoginRequest request) {
        User user = userRepository.findByUsername(request.username())
                .orElseThrow(() -> new BusinessException(
                        HttpStatus.UNAUTHORIZED, "帳號或密碼錯誤"));

        // matches(原始密碼, 雜湊)：BCrypt 內建加鹽，同密碼每次雜湊結果都不同
        if (!passwordEncoder.matches(request.password(), user.getPassword())) {
            throw new BusinessException(HttpStatus.UNAUTHORIZED, "帳號或密碼錯誤");
        }
        return jwtService.generateToken(user);
    }
}
```

**逐段講解：**

- **`@Transactional` 預設行為**：方法內任何 `RuntimeException` 拋出 → 全部回滾。註冊只有單一 save，看似不需要；但加上它是好習慣——之後加「送歡迎優惠券」等第二個寫入時就自動有原子性。
- **`readOnly = true`**：提示 Hibernate 與連線池「只讀不寫」，可省 dirty-check 開銷；查詢型方法建議加上。
- **錯誤訊息刻意含糊**：「帳號或密碼錯誤」而不說「帳號不存在」——否則攻擊者可以藉由錯誤訊息差異**枚舉有效帳號**（username enumeration）。
- **兩次檢查 vs 資料庫唯一鍵**：`existsByUsername` 提供友善錯誤訊息；`uk_users_username` 唯一約束是並發時的最後防線（兩人同時註冊同名，其中一人會收到 500 → 進階練習可把它轉成 409）。

### 7.3 OrderService — 核心商業邏輯（下單計價 / 擁有權 / 狀態規則）

```java
// src/main/java/com/restaurant/ordersystem/service/OrderService.java
package com.restaurant.ordersystem.service;

import com.restaurant.ordersystem.dto.request.OrderCreateRequest;
import com.restaurant.ordersystem.dto.request.OrderItemRequest;
import com.restaurant.ordersystem.dto.request.OrderUpdateRequest;
import com.restaurant.ordersystem.dto.response.OrderDetailResponse;
import com.restaurant.ordersystem.dto.response.OrderItemResponse;
import com.restaurant.ordersystem.dto.response.OrderSummaryResponse;
import com.restaurant.ordersystem.dto.response.StatusCountResponse;
import com.restaurant.ordersystem.entity.*;
import com.restaurant.ordersystem.exception.BusinessException;
import com.restaurant.ordersystem.exception.ResourceNotFoundException;
import com.restaurant.ordersystem.repository.MenuItemRepository;
import com.restaurant.ordersystem.repository.OrderRepository;
import com.restaurant.ordersystem.repository.UserRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final MenuItemRepository menuItemRepository;
    private final UserRepository userRepository;

    // ===================== 使用者端 =====================

    /** 下單：只收 menuItemId + quantity，價格一律後端查表 */
    @Transactional
    public OrderDetailResponse createOrder(Long userId, OrderCreateRequest request) {
        List<OrderItem> items = buildOrderItems(request.items());
        User user = userRepository.getReferenceById(userId); // 取代理物件，不發 SQL

        Order order = new Order(user);
        items.forEach(order::addItem);   // 領域方法：同步雙向關聯 + 重算總價

        Order saved = orderRepository.save(order); // cascade=ALL 連明細一起 INSERT
        return toDetail(saved);
    }

    /** 我的訂單（分頁） */
    @Transactional(readOnly = true)
    public Page<OrderSummaryResponse> getMyOrders(Long userId, Pageable pageable) {
        return orderRepository.findByUserId(userId, pageable).map(this::toSummary);
    }

    /** 我的單筆訂單（含明細） */
    @Transactional(readOnly = true)
    public OrderDetailResponse getMyOrder(Long userId, Long orderId) {
        return toDetail(findOwnedOrder(orderId, userId));
    }

    /** 修改訂單：僅限本人 + PENDING 狀態 */
    @Transactional
    public OrderDetailResponse updateMyOrder(Long userId, Long orderId,
                                            OrderUpdateRequest request) {
        Order order = findOwnedOrder(orderId, userId);
        ensureEditable(order);
        order.replaceItems(buildOrderItems(request.items())); // 換明細 + orphanRemoval 刪舊
        return toDetail(orderRepository.save(order));          // @Version 自動 +1
    }

    /** 取消訂單：僅限本人 + PENDING 狀態（軟刪除概念：狀態改 CANCELLED） */
    @Transactional
    public void cancelMyOrder(Long userId, Long orderId) {
        Order order = findOwnedOrder(orderId, userId);
        ensureEditable(order);
        order.setStatus(OrderStatus.CANCELLED);
        orderRepository.save(order);
    }

    // ===================== 管理後台 =====================

    /** 全部訂單（分頁，可依狀態過濾） */
    @Transactional(readOnly = true)
    public Page<OrderSummaryResponse> getAllOrders(OrderStatus status, Pageable pageable) {
        Page<Order> page = (status == null)
                ? orderRepository.findAllWithUser(pageable)
                : orderRepository.findByStatus(status, pageable);
        return page.map(this::toSummary);
    }

    /** 任一單筆訂單（含明細） */
    @Transactional(readOnly = true)
    public OrderDetailResponse getOrder(Long orderId) {
        Order order = orderRepository.findByIdWithItems(orderId)
                .orElseThrow(() -> new ResourceNotFoundException("找不到訂單：" + orderId));
        return toDetail(order);
    }

    /** 各狀態訂單數統計（介面投射） */
    @Transactional(readOnly = true)
    public List<StatusCountResponse> getStats() {
        return orderRepository.countGroupByStatus().stream()
                .map(sc -> new StatusCountResponse(sc.getStatus(), sc.getCount()))
                .toList();
    }

    /** 更新訂單狀態（店家接單/出餐） */
    @Transactional
    public OrderSummaryResponse updateStatus(Long orderId, OrderStatus newStatus) {
        Order order = orderRepository.findByIdWithItems(orderId)
                .orElseThrow(() -> new ResourceNotFoundException("找不到訂單：" + orderId));
        order.setStatus(newStatus);
        return toSummary(orderRepository.save(order));
    }

    /** 刪除訂單：cascade + orphanRemoval 會連明細一起刪 */
    @Transactional
    public void deleteOrder(Long orderId) {
        if (!orderRepository.existsById(orderId)) {
            throw new ResourceNotFoundException("找不到訂單：" + orderId);
        }
        orderRepository.deleteById(orderId);
    }

    // ===================== 私有方法 =====================

    /**
     * 把「前端願望清單」變成「可入庫的明細」。
     * 三大原則：合併重複、一次查表、價格快照。
     */
    private List<OrderItem> buildOrderItems(List<OrderItemRequest> itemRequests) {
        // 1) 合併重複品項：同 menuItemId 累加數量
        Map<Long, Integer> quantityMap = new LinkedHashMap<>();
        itemRequests.forEach(r -> quantityMap.merge(r.menuItemId(), r.quantity(), Integer::sum));

        // 2) 一次查所有品項：findAllById → WHERE id IN (...)（避免逐筆 findById 的 N+1）
        List<MenuItem> menuItems = menuItemRepository.findAllById(quantityMap.keySet());
        if (menuItems.size() != quantityMap.size()) {
            // 查回數量比請求少 → 有不存在的 menuItemId
            throw new ResourceNotFoundException("訂單內含不存在的菜單品項");
        }

        // 3) 逐一檢查供應狀態；OrderItem 建構子自動做價格快照
        return menuItems.stream()
                .map(mi -> {
                    if (!mi.isAvailable()) {
                        throw new BusinessException(HttpStatus.CONFLICT,
                                "品項已下架：" + mi.getName());
                    }
                    return new OrderItem(mi, quantityMap.get(mi.getId()));
                })
                .toList();
    }

    /** 查單筆 + 驗擁有權；不是本人的訂單一律 404（不透露存在性） */
    private Order findOwnedOrder(Long orderId, Long userId) {
        Order order = orderRepository.findByIdWithItems(orderId)
                .orElseThrow(() -> new ResourceNotFoundException("找不到訂單：" + orderId));
        if (!order.getUser().getId().equals(userId)) {
            throw new ResourceNotFoundException("找不到訂單：" + orderId);
        }
        return order;
    }

    /** 「尚未出餐才能改」的商業規則 */
    private void ensureEditable(Order order) {
        if (!order.isEditable()) {
            throw new BusinessException(HttpStatus.CONFLICT,
                    "訂單狀態為「" + order.getStatus().getLabel() + "」，已無法修改或取消");
        }
    }

    // ---- Entity → DTO 轉換（在交易內完成，配合 open-in-view=false） ----

    private OrderSummaryResponse toSummary(Order order) {
        return new OrderSummaryResponse(
                order.getId(),
                order.getUser().getUsername(),   // JOIN FETCH 已抓，不觸發查詢
                order.getStatus(),
                order.getTotalAmount(),
                order.getCreatedAt());
    }

    private OrderDetailResponse toDetail(Order order) {
        List<OrderItemResponse> items = order.getItems().stream()
                .map(i -> new OrderItemResponse(
                        i.getItemName(), i.getUnitPrice(),
                        i.getQuantity(), i.getSubtotal()))
                .toList();
        return new OrderDetailResponse(
                order.getId(),
                order.getUser().getUsername(),
                order.getStatus(),
                order.getTotalAmount(),
                order.getCreatedAt(),
                items);
    }
}
```

**逐段講解（本文件最核心的一段）：**

1. **`createOrder` — 修掉「價格竄改」漏洞（問題 #9）**
   前端只送 `{menuItemId, quantity}`。價格來自 `menu_items` 表，`OrderItem` 建構子快照 `unitPrice`，`order.addItem()` 重算 `totalAmount`。**從頭到尾沒有任何一個數字來自前端**。
2. **`getReferenceById` vs `findById`**
   `getReferenceById(userId)` 回傳 LAZY 代理（不發 SQL），存訂單時直接把 FK `user_id` 寫進去。`findById` 會真的 SELECT。建立關聯時用前者更省。
3. **合併重複品項**
   前端把「牛肉麵×2」+「牛肉麵×1」分成兩列送也不會錯：`Map.merge()` 累加成 3。進一步靠 DTO `@Min(1)/@Max(99)` 保證單列數量合法。
4. **`findAllById` 一次查表**
   點 5 道菜 = 1 次 `WHERE id IN (1,3,5,7,9)`，不是 5 次。
5. **`findOwnedOrder` — 擁有權與 404 策略（問題 #11）**
   「不是你的訂單」與「不存在的訂單」回同樣的 404。若回 403，等於告訴攻擊者「這個訂單編號存在喔」。
6. **`replaceItems` + `orphanRemoval` — 修掉「孤兒明細」（問題 #3）**
   修改訂單 = 清單重放。提交時 Hibernate 自動刪舊明細、插新明細，不殘留垃圾。
7. **`toSummary` / `toDetail` — Entity 不出 Service**
   我們把 Entity 轉成 DTO **在交易內**完成（`open-in-view=false` 下 LAZY 存取唯一合法的地方），Controller 拿到的已是純資料。

> ⚠️ **`@Transactional` 的 rollback 示範（練習 7.6）**
> `createOrder` 若在最後一刻拋例外（例如最後一個品項下架），前面已建立的訂單與明細**全部回滾**，資料庫不留半套資料——這正是原始架構（無 Service、無交易）做不到的保證。11.5 有實測步驟。

### 7.5 Service 層交易行為總表

| 方法 | 交易 | 讀寫 | 回滾時機 |
| --- | --- | --- | --- |
| `register` | `@Transactional` | 讀寫 | 帳號重複（409） |
| `login` | `@Transactional(readOnly=true)` | 只讀 | — |
| `createOrder` | `@Transactional` | 讀寫 | 品項不存在（404）/ 已下架（409）→ 訂單與明細整包回滾 |
| `updateMyOrder` / `cancelMyOrder` | `@Transactional` | 讀寫 | 非本人（404）/ 非 PENDING（409） |
| `updateStatus` / `deleteOrder` | `@Transactional` | 讀寫 | 樂觀鎖衝突（409，見 7.6） |
| 查詢類 | `@Transactional(readOnly=true)` | 只讀 | — |

> 💡 `@Transactional` 只攔**同類別外部呼叫**（走代理）。Service 內部方法互 call 不會啟動新交易——所以「需要交易的方法」一律作為 Service 的公開方法由 Controller 呼叫。

### 7.6 樂觀鎖實戰（@Version）

情境：店家（admin）在改訂單狀態的同時，顧客正在修改同一筆訂單。

```
時間軸  要求A（顧客 PUT 明細）                要求B（店家 PUT 狀態）
 t1    讀出 order（version = 3）
 t2                                         讀出 order（version = 3）
 t3    提交：UPDATE orders SET ..., version=4
       WHERE id=? AND version=3  ✅成功
 t4                                         提交：UPDATE orders SET ..., version=4
                                            WHERE id=? AND version=3  ❌0 列 →
                                            ObjectOptimisticLockingFailureException
                                            → GlobalExceptionHandler → HTTP 409
```

沒有 `@Version` 的話，t4 會直接成功並**整筆覆寫** t3 的修改（顧客改的明細憑空消失）。有了它，後到者收到明確的 409，前端可提示「資料已被更新，請重新整理」。

## 8. 安全性設計（JWT + Spring Security）

### 8.1 驗證流程總覽

```
【登入】
前端 ── POST /api/auth/login {username, password} ──► AuthService
       （BCrypt 比對成功）──► JwtService 產生 Token（簽章內含 userId/username/role）
前端 ◄── { token: "eyJhbGciOi..." } （存 localStorage）

【受保護的 API 呼叫】
前端 ── GET /api/orders/my ＋ Header「Authorization: Bearer eyJhbGciOi...」──►
       JwtAuthFilter（每次請求都先跑）：
         1. 取出 Bearer Token
         2. 驗簽＋檢查過期（Jwts.parser().verifyWith(key)...）
         3. 解出 userId / username / role → 建立 UserPrincipal
         4. 寫入 SecurityContext（=「這個請求是誰」）
       SecurityConfig 的規則接力：
         /api/auth/**        → 放行（登入註冊本來就要能打）
         GET /api/menu/**    → 放行（看菜單不用登入）
         /api/admin/**       → 需要ROLE_ADMIN
         其他 /api/**        → 需要已登入
       Controller 用 @AuthenticationPrincipal 拿到「我是誰」
```

> 💡 與 Session 的差異（規劃書比較表的延伸）：JWT 把身分「簽在 Token 裡」，後端**不存任何登入狀態**（STATELESS）——橫向擴充多台伺服器不用共享 Session；代價是 Token 在效期內難註銷（所以效期要短，進階做法見練習題 4）。

### 8.2 JwtService — 產生與解析 Token

```java
// src/main/java/com/restaurant/ordersystem/security/JwtService.java
package com.restaurant.ordersystem.security;

import com.restaurant.ordersystem.dto.response.TokenResponse;
import com.restaurant.ordersystem.entity.User;
import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;

import javax.crypto.SecretKey;
import java.nio.charset.StandardCharsets;
import java.time.Instant;
import java.util.Date;

/**
 * JWT 的「鑄造與驗鈔」中心。
 * HS256 對稱式簽章：同一把金鑰負責簽發與驗證。
 */
@Service
public class JwtService {

    private final SecretKey key;
    private final long expirationMs;
    private final String issuer;

    public JwtService(@Value("${app.jwt.secret}") String secret,
                      @Value("${app.jwt.expiration-ms}") long expirationMs,
                      @Value("${app.jwt.issuer}") String issuer) {
        // HS256 金鑰至少 256 bits（32 bytes），否則 Keys.hmacShaKeyFor 會拋錯
        this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
        this.expirationMs = expirationMs;
        this.issuer = issuer;
    }

    /** 登入成功 → 鑄造 Token */
    public TokenResponse generateToken(User user) {
        Instant now = Instant.now();
        String token = Jwts.builder()
                .subject(String.valueOf(user.getId()))      // sub：使用者 ID
                .claim("username", user.getUsername())     // 自訂聲明
                .claim("role", user.getRole().name())
                .issuer(issuer)                              // iss：簽發者
                .issuedAt(Date.from(now))                    // iat：簽發時間
                .expiration(Date.from(now.plusMillis(expirationMs))) // exp：到期
                .signWith(key)                               // HS256 簽章
                .compact();
        return new TokenResponse(token, "Bearer",
                expirationMs / 1000, user.getUsername(), user.getRole().name());
    }

    /**
     * 驗鈕：驗簽＋檢查過期＋檢查簽發者。
     * 失敗（過期/改竄/非本系統簽發）會拋 JwtException，由呼叫端處理。
     */
    public Claims parseToken(String token) {
        return Jwts.parser()
                .verifyWith(key)
                .requireIssuer(issuer)
                .build()
                .parseSignedClaims(token)   // 驗證失敗拋 ExpiredJwtException 等
                .getPayload();              // Claims（sub/username/role/...）
    }
}
```

**逐段講解：**

- **Token 內容**（Payload，`sub`/`iss`/`iat`/`exp` 是 RFC 7519 標準欄位）：
  ```json
  {
    "sub": "2", "username": "amy", "role": "USER",
    "iss": "restaurant-ordering-system",
    "iat": 1762000000, "exp": 1762003600
  }
  ```
  Payload 只是 **Base64 編碼**，**任何人都能解開看**（試試把 token 貼到 jwt.io）——所以**絕對不能放密碼等敏感資料**；但沒有金鑰就改不了內容（改了簽章對不上），這就是「不可偽造、但可閱讀」。
- **`signWith(key)`**：不指定演算法時，JJWT 依金鑰型別自動選 HS256（`SecretKey`）。
- **`parseSignedClaims`** 一次完成：簽章驗證、`exp` 過期檢查、`requireIssuer` 簽發者檢查。任何一項失敗拋 `JwtException` 子類。

> ⚠️ **JWT 三大安全守則**：
> 1. 金鑰至少 32 bytes（HS256 規定），且**絕不進版控**——本專案用 `${JWT_SECRET:預設}` 讓正式環境以環境變數覆寫。
> 2. 效期短（1 小時內）：Token 被偷走的最大損失 = 效期長度。
> 3. 用 HTTPS：Bearer Token 在 header 明文傳輸，HTTP 環境等於裸奔。

### 8.3 UserPrincipal — 「目前的使用者」

```java
// src/main/java/com/restaurant/ordersystem/security/UserPrincipal.java
package com.restaurant.ordersystem.security;

import com.restaurant.ordersystem.entity.Role;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.userdetails.UserDetails;

import java.util.Collection;
import java.util.List;

/** 從 JWT 解出來的「這次請求是誰」；實作 UserDetails 以便掛進 SecurityContext */
public record UserPrincipal(Long id, String username, Role role) implements UserDetails {

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        // Spring Security 慣例：角色前面加 ROLE_，對應 hasRole("ADMIN")
        return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));
    }

    @Override public String getPassword() { return null; }   // Token 機制不需要
    @Override public String getUsername() { return username; }
    @Override public boolean isAccountNonExpired() { return true; }
    @Override public boolean isAccountNonLocked() { return true; }
    @Override public boolean isCredentialsNonExpired() { return true; }
    @Override public boolean isEnabled() { return true; }
}
```

**說明：** record 一行搞定不可變的「使用者快照」。Controller 端用 `@AuthenticationPrincipal UserPrincipal p` 直接拿到 `p.id()`。`getAuthorities()` 的 `ROLE_` 前綴是 `hasRole()` 的搭配慣例（`hasAuthority("ROLE_ADMIN")` 則不幫你加）。

### 8.4 JwtAuthFilter — 每個請求的守門員

```java
// src/main/java/com/restaurant/ordersystem/security/JwtAuthFilter.java
package com.restaurant.ordersystem.security;

import com.restaurant.ordersystem.entity.Role;
import io.jsonwebtoken.Claims;
import io.jsonwebtoken.JwtException;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpHeaders;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;

/**
 * OncePerRequestFilter：保證每個請求只跑一次（forward/include 不重複觸發）。
 */
@Component
@RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtService jwtService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {

        String header = request.getHeader(HttpHeaders.AUTHORIZATION);

        // 只處理「Bearer xxx」格式的請求；沒帶就放行（後面的規則決定要不要擋）
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);
            try {
                Claims claims = jwtService.parseToken(token);   // 驗鈔

                UserPrincipal principal = new UserPrincipal(
                        Long.valueOf(claims.getSubject()),      // sub = userId
                        claims.get("username", String.class),
                        Role.valueOf(claims.get("role", String.class)));

                UsernamePasswordAuthenticationToken authentication =
                        new UsernamePasswordAuthenticationToken(
                                principal, null, principal.getAuthorities());

                SecurityContextHolder.getContext().setAuthentication(authentication);
            } catch (JwtException | IllegalArgumentException e) {
                // 無效/過期 Token：清空身分，視同未登入（由後續規則回 401）
                SecurityContextHolder.clearContext();
            }
        }
        filterChain.doFilter(request, response);   // 繼續往後走（很關鍵，不能漏）
    }
}
```

**逐段講解：**

- 沒帶 Token → 不設身分 → `anyRequest().authenticated()` 的規則會擋 → 401。
- 帶了假 Token → `parseToken` 拋 `JwtException` → 清空 context → 一樣 401。
- 帶了好 Token → 身分寫入 `SecurityContextHolder` → 後續 `@AuthenticationPrincipal`、`hasRole(...)` 都能用。

### 8.5 SecurityConfig — 安全規則總指揮

```java
// src/main/java/com/restaurant/ordersystem/security/SecurityConfig.java
package com.restaurant.ordersystem.security;

import lombok.RequiredArgsConstructor;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.http.HttpStatus;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.CorsConfigurationSource;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;

import java.io.IOException;
import java.time.LocalDateTime;
import java.util.List;

@Configuration
@EnableWebSecurity
@EnableMethodSecurity          // 打開 @PreAuthorize（方法級權限）
@RequiredArgsConstructor
public class SecurityConfig {

    private final JwtAuthFilter jwtAuthFilter;

    /** CORS 白名單：來自 application.properties，取代原始程式的 origins="*" */
    @Value("${app.cors.allowed-origins}")
    private String[] allowedOrigins;

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            // 1) 關閉 CSRF：我們用 Token 而非 Cookie，沒有 CSRF 風險面
            .csrf(AbstractHttpConfigurer::disable)

            // 2) CORS：使用下方的 corsConfigurationSource()
            .cors(Customizer.withDefaults())

            // 3) STATELESS：完全不建立 HttpSession（JWT 精神）
            .sessionManagement(s ->
                    s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))

            // 4) URL 規則（RBAC）：由上而下比對，先命中先生效
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()          // 註冊/登入
                .requestMatchers(HttpMethod.GET, "/api/menu/**").permitAll() // 看菜單
                .requestMatchers("/swagger-ui/**", "/v3/api-docs/**").permitAll() // API 文件
                .requestMatchers("/api/admin/**").hasRole("ADMIN")     // 後台：限管理者
                .anyRequest().authenticated())                        // 其餘：要登入

            // 5) 401/403 改回 JSON（預設是空的狀態碼，前端很難處理）
            .exceptionHandling(ex -> ex
                .authenticationEntryPoint((req, res, e) ->
                        writeJsonError(res, HttpStatus.UNAUTHORIZED, "尚未登入或 Token 無效"))
                .accessDeniedHandler((req, res, e) ->
                        writeJsonError(res, HttpStatus.FORBIDDEN, "權限不足")))

            // 6) 把 JWT 過濾器掛在使用者密碼驗證器之前
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }

    /** 密碼雜湊器：BCrypt（自帶鹽、可調強度 cost=10） */
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    /** CORS 細部規則 */
    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(List.of(allowedOrigins));  // 明確白名單
        config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
        config.setAllowedHeaders(List.of("*"));
        config.setAllowCredentials(true);                   // 允許帶 cookie/授權資訊
        config.setMaxAge(3600L);                            // 預檢結果快取 1 小時

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return source;
    }

    /** 手寫的小工具：把錯誤以 JSON 回給前端 */
    private void writeJsonError(jakarta.servlet.http.HttpServletResponse response,
                                HttpStatus status, String message) throws IOException {
        response.setStatus(status.value());
        response.setContentType("application/json");
        response.setCharacterEncoding("UTF-8");
        response.getWriter().write(
            "{\"timestamp\":\"%s\",\"status\":%d,\"error\":\"%s\",\"message\":\"%s\",\"fieldErrors\":{}}"
                .formatted(LocalDateTime.now(), status.value(),
                           status.getReasonPhrase(), message));
    }
}
```

**逐段講解：**

- **規則順序**：`requestMatchers` 由上而下，第一個命中的生效——`/api/admin/**` 放在 `anyRequest()` 前面才攔得到 ADMIN 限定。
- **`hasRole("ADMIN")`** 自動補 `ROLE_` 前綴，對應 `UserPrincipal.getAuthorities()` 的 `ROLE_ADMIN`。
- **CSRF 為何能關**：CSRF 攻擊的是「瀏覽器自動附帶 Cookie」的機制；我們的 Token 放在 `Authorization` header，瀏覽器不會自動帶，攻擊者網頁也無法偽造（跨站讀不到 localStorage）。
- **`writeJsonError`**：讓 401/403 有跟 9.8 統一格式一致的 JSON 本文（訊息固定字串，不涉及跳脫）。

> ⚠️ **CORS 白名單與 `allowCredentials(true)`**：兩者搭配時**不能**用 `*`（規格禁止），Spring 會直接拒絕啟動。這也再次印證「`origins="*"` 不是好 defaults」。

## 9. Controller 層與 API 設計（含 DTO、例外處理、Swagger）

### 9.1 為什麼用 DTO，不直接回傳 Entity？

| 直接回 Entity 的問題 | DTO 的解法 |
| --- | --- |
| LAZY 關聯序列化時才觸發查詢（`open-in-view=false` 下直接報錯） | DTO 組裝在 Service 交易內完成 |
| **內部欄位外洩**：如 `User.password`（雜湊）、`version`、內部 ID 結構 | DTO 只宣告要暴露的欄位 |
| API 合約綁死資料表結構：加一個欄位 = 前端全部受影響 | 資料表演化不影響 API 合約 |
| `Map<String,Object>` 無型別、IDE 無法提示、重構會漏改 | record 編譯期就檢查 |

```java
// src/main/java/com/restaurant/ordersystem/exception/GlobalExceptionHandler.java
package com.restaurant.ordersystem.exception;

import com.restaurant.ordersystem.dto.response.ApiError;
import jakarta.servlet.http.HttpServletRequest;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.orm.ObjectOptimisticLockingFailureException;
import org.springframework.security.access.AccessDeniedException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.method.annotation.MethodArgumentTypeMismatchException;

import java.time.LocalDateTime;
import java.util.LinkedHashMap;
import java.util.Map;

/**
 * 全域例外處理：所有 Controller 拋出的例外都在這裡轉成「統一格式的 JSON + 正確狀態碼」。
 * 原始程式沒有這層，任何錯誤都是 500 + stack trace 外洩。
 */
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    /** 404：找不到資源 */
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiError> handleNotFound(ResourceNotFoundException ex,
                                                  HttpServletRequest req) {
        return build(HttpStatus.NOT_FOUND, ex.getMessage(), req, null);
    }

    /** 依商業例外自帶的狀態碼回應（409 衝突 / 401 帳密錯誤…） */
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ApiError> handleBusiness(BusinessException ex,
                                                   HttpServletRequest req) {
        return build(ex.getStatus(), ex.getMessage(), req, null);
    }

    /** 400：@Valid 驗證失敗，逐欄位列出錯誤訊息 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiError> handleValidation(MethodArgumentNotValidException ex,
                                                     HttpServletRequest req) {
        Map<String, String> fieldErrors = new LinkedHashMap<>();
        ex.getBindingResult().getFieldErrors()
                .forEach(fe -> fieldErrors.putIfAbsent(fe.getField(), fe.getDefaultMessage()));
        return build(HttpStatus.BAD_REQUEST, "請求參數驗證失敗", req, fieldErrors);
    }

    /** 400：JSON 格式錯誤 / 路徑變數、查詢參數型別錯誤（如 status=打錯字） */
    @ExceptionHandler({HttpMessageNotReadableException.class,
                       MethodArgumentTypeMismatchException.class})
    public ResponseEntity<ApiError> handleUnreadable(Exception ex, HttpServletRequest req) {
        return build(HttpStatus.BAD_REQUEST, "請求格式或參數值不正確", req, null);
    }

    /** 403：已登入但權限不足（@PreAuthorize 攔下來的會走到這） */
    @ExceptionHandler(AccessDeniedException.class)
    public ResponseEntity<ApiError> handleAccessDenied(AccessDeniedException ex,
                                                       HttpServletRequest req) {
        return build(HttpStatus.FORBIDDEN, "權限不足", req, null);
    }

    /** 409：樂觀鎖衝突（@Version，兩邊同時改同一筆） */
    @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
    public ResponseEntity<ApiError> handleOptimisticLock(
            ObjectOptimisticLockingFailureException ex, HttpServletRequest req) {
        return build(HttpStatus.CONFLICT, "資料已被其他請求修改，請重新整理後再試", req, null);
    }

    /** 500：保底。記 log 供排查，但不把內部細節回給前端 */
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> handleUnexpected(Exception ex, HttpServletRequest req) {
        log.error("未預期的錯誤 path={}", req.getRequestURI(), ex);
        return build(HttpStatus.INTERNAL_SERVER_ERROR, "系統發生未預期的錯誤，請稍後再試",
                     req, null);
    }

    private ResponseEntity<ApiError> build(HttpStatus status, String message,
                                           HttpServletRequest req,
                                           Map<String, String> fieldErrors) {
        ApiError body = new ApiError(
                LocalDateTime.now(), status.value(), status.getReasonPhrase(),
                message, req.getRequestURI(),
                fieldErrors == null ? Map.of() : fieldErrors);
        return ResponseEntity.status(status).body(body);
    }
}
```

```java
        OrderDetailResponse response = orderService.createOrder(principal.id(), request);
        // 201 + Location 標頭指向新資源的查詢位置（REST 慣例）
        return ResponseEntity
                .created(URI.create("/api/orders/my/" + response.orderId()))
                .body(response);
    }

    @GetMapping("/my")
    @Operation(summary = "我的訂單（分頁）",
               description = "參數範例：?page=0&size=10&sort=createdAt,desc")
    public PageResponse<OrderSummaryResponse> getMyOrders(
            @AuthenticationPrincipal UserPrincipal principal,
            @ParameterObject Pageable pageable) {
        return PageResponse.from(orderService.getMyOrders(principal.id(), pageable));
    }

    @GetMapping("/my/{id}")
    @Operation(summary = "我的單筆訂單（含明細）")
    public OrderDetailResponse getMyOrder(
            @AuthenticationPrincipal UserPrincipal principal,
            @PathVariable Long id) {
        return orderService.getMyOrder(principal.id(), id);
    }

    @PutMapping("/my/{id}")
    @Operation(summary = "修改訂單內容（限 PENDING 狀態）")
    @ApiResponses({
        @ApiResponse(responseCode = "200", description = "修改成功"),
        @ApiResponse(responseCode = "404", description = "訂單不存在或不屬於你"),
        @ApiResponse(responseCode = "409", description = "訂單已不可修改")
    })
    public OrderDetailResponse updateMyOrder(
            @AuthenticationPrincipal UserPrincipal principal,
            @PathVariable Long id,
            @Valid @RequestBody OrderUpdateRequest request) {
        return orderService.updateMyOrder(principal.id(), id, request);
    }

    @DeleteMapping("/my/{id}")
    @Operation(summary = "取消訂單（限 PENDING 狀態，改為 CANCELLED）")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void cancelMyOrder(
            @AuthenticationPrincipal UserPrincipal principal,
            @PathVariable Long id) {
        orderService.cancelMyOrder(principal.id(), id);
    }
}
```

**逐段講解：**

- **`@AuthenticationPrincipal UserPrincipal principal`**：從 SecurityContext 拿「本請求是誰」——`principal.id()` 就是 JWT 的 `sub`。**使用者身分永遠取自 Token，不取自請求參數**（否則又是竄改漏洞）。
- **`@ParameterObject Pageable`**：Spring Data 自動把 `?page=&size=&sort=` 綁成 Pageable；springdoc 這個註解讓 Swagger 顯示分頁參數。
- **狀態碼**：建立 201 + Location、成功 200、取消成功 204（無內容）、驗證失敗 400、不屬於你 404、不可修改 409。

### 10.2 DataInitializer — 建立測試帳號（BCrypt）

> ⚠️ **為什麼帳號不用 data.sql 建？** BCrypt 雜湊值必須由 `PasswordEncoder.encode()` 現場產生（同一密碼每次雜湊都不同），手寫進 SQL 既麻煩也不可靠。用 `CommandLineRunner` 在啟動時建，程式碼即文件。

```java
// src/main/java/com/restaurant/ordersystem/bootstrap/DataInitializer.java
package com.restaurant.ordersystem.bootstrap;

import com.restaurant.ordersystem.entity.Role;
import com.restaurant.ordersystem.entity.User;
import com.restaurant.ordersystem.repository.UserRepository;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.boot.CommandLineRunner;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Component;

/** 啟動時確保測試帳號存在（冪等：已存在就跳過） */
@Slf4j
@Component
@RequiredArgsConstructor
public class DataInitializer implements CommandLineRunner {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;

    @Override
    public void run(String... args) {
        if (!userRepository.existsByUsername("user1")) {
            userRepository.save(new User(
                    "user1", passwordEncoder.encode("123456"), Role.USER));
            log.info("已建立測試帳號：user1 / 123456");
        }
        if (!userRepository.existsByUsername("admin")) {
            userRepository.save(new User(
                    "admin", passwordEncoder.encode("admin123"), Role.ADMIN));
            log.info("已建立測試帳號：admin / admin123");
        }
    }
}
```

**說明：** `CommandLineRunner` 在 Spring Boot 完成啟動後執行一次；用 `existsByUsername` 保證冪等（重啟不會重複建立）。測試帳號沿用規劃書：`user1 / 123456`、`admin / admin123`。

### 10.3 啟動後自動完成的資料

| 資料 | 來源 | 時機 |
| --- | --- | --- |
| 4 張資料表（users/menu_items/orders/order_items）+ FK + 唯一約束 | Hibernate `ddl-auto=create-drop` | 啟動建表、關閉刪表 |
| 9 道菜 | `data.sql` | 建表後由 Spring SQL init 執行 |
| 2 個測試帳號（BCrypt） | `DataInitializer` | 啟動完成後 |

### 11.5 驗證「優化」本身的三個實驗

**實驗 1：N+1 與 JOIN FETCH（看 console SQL）**

把 `OrderRepository.findByUserId` 的 `JOIN FETCH o.user` 暫時註解掉重啟，呼叫 `GET /api/orders/my`（size=10）→ console 出現 **1 + 10 次** SELECT。加回來 → 只剩 **1 次** JOIN 查詢：

```sql
-- 有 JOIN FETCH（優化後，只此一次）：
select o1_0.id, ..., u1_0.id, u1_0.username, ...
from orders o1_0 join users u1_0 on u1_0.id = o1_0.user_id
where u1_0.id = ? limit ?, ?
```

**實驗 2：交易回滾**

用 SQL 把某品項標成下架：`UPDATE menu_items SET available = false WHERE id = 9;`
（重啟後 data.sql 會重建，實驗前做即可）然後下單：

```json
{ "items": [ { "menuItemId": 1, "quantity": 1 }, { "menuItemId": 9, "quantity": 1 } ] }
```

預期：409「品項已下架：綠茶」，且資料庫**沒有任何新訂單**（`SELECT COUNT(*) FROM orders;` 不變）——前面的牛肉麵明細也一起回滾了。

**實驗 3：樂觀鎖（併發衝突）**

開兩個瀏覽器分頁都用 admin 登入：

1. 分頁 A 與 B 都先 `GET /api/admin/orders/{id}`（此時 version 相同，例如 3）。
2. 分頁 A `PUT /api/admin/orders/{id}/status` `{"status":"CONFIRMED"}` → 200（version → 4）。
3. 分頁 B `PUT /api/admin/orders/{id}/status` `{"status":"COMPLETED"}` → **409**「資料已被其他請求修改」。

沒有 `@Version` 時，第 3 步會成功並覆蓋 A 的結果——本實驗證明後寫入者被擋下。


1. 接上 `GET /api/admin/orders/revenue?days=30`（限 ADMIN）。
2. 回 `{ "totalRevenue": 12345.00, "since": "...", "orderCount": 12 }`（`orderCount` 用另一個 count 查詢）。

**完成標準**：取消的訂單不計入；`days` 用 `@Min(1) @Max(365)` 驗證。

### 練習 3：訂單狀態轉移規則（★★）

目前 `updateStatus` 可以任意改狀態（如 COMPLETED → PENDING）。請實作狀態機：

```
PENDING    → CONFIRMED, CANCELLED
CONFIRMED  → COMPLETED, CANCELLED
COMPLETED  → （終態）
CANCELLED  → （終態）
```

提示：在 `OrderStatus` 加 `Set<OrderStatus> allowedTransitions()`（或用 `EnumSet`），在 Service 檢查，不合法就拋 `BusinessException(409)`。

**完成標準**：COMPLETED → PENDING 回 409，錯誤訊息含目前狀態與不允許的原因；`GET /api/admin/orders/stats` 不受影響。

### 練習 4：JWT 進階（★★★）

1. **Refresh Token**：`POST /api/auth/refresh` 帶舊 token（效期 7 天、scope=refresh）換發新的 access token。
2. **登出黑名單**：記錄已登出 token 的 jti（JWT ID）到資料庫或記憶體快取，`JwtAuthFilter` 檢查命中即拒絕。

**完成標準**：登出後舊 token 呼叫 `GET /api/orders/my` 回 401；refresh 過期後必須重新登入。

### 練習 5：自動化測試（★★★）

1. **Repository 層**（`@DataJpaTest`）：測 `countGroupByStatus` 與 `findByIdWithItems`（驗證明細真的被抓出來）。
2. **Web 層**（`@SpringBootTest` + `MockMvc`）：完整打一輪「註冊 → 登入 → 下單 → 查詢 → 403 驗證（USER 打 admin API）」。

提示：測試資料庫可用 H2 相容模式（`jdbc:h2:mem:test;MODE=MySQL`）或 Testcontainers。**完成標準**：`mvn test` 綠燈，涵蓋 200/201/400/401/403/404/409 各至少一例。
